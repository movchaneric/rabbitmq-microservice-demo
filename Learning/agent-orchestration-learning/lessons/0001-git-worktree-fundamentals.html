Lesson 1 — One repo, many rooms

Git worktrees: the physical isolation every worker agent in this track will stand on.

Right now, when you work in a git repo, you have exactly one working directory and one branch checked out at a time. Want to work on two branches "at once"? You stash, switch, unstash — or you clone the whole repo again into a second folder and pay for a second full copy of history. Neither scales to "five agents, five branches, all running right now." Worktrees are git's actual answer to that problem, and they're the ground floor of everything else in this track: a worker agent can't safely touch its own branch in its own directory unless something set that directory up first.

By the end of this lesson you'll have created a linked worktree, made an independent commit in it, watched both worktrees share one `.git` history, and cleaned it up — by hand, no agent involved yet. That muscle is what Lesson 3 hands to a worker agent.

The one idea that trips everyone up

A worktree is not a clone. A clone duplicates the entire .git object store — every commit, every blob — onto disk a second time. A linked worktree shares the same .git object store with the original checkout; it only adds a new working directory plus a small bit of metadata recording which branch that directory has checked out. One repository's history, several rooms to stand in it.

ApproachWorking dirs.git object storeBranches checked out at once
Plain checkout11 (shared, obviously)1
git clone again2 (separate repos)2 — full duplicate2, but they don't know about each other
git worktree add2 (linked)1 — shared2, same repo, same history

— Git's own docs: "a repository can have one main working tree and any number of additional linked working trees." See the official git-worktree reference.

Why this matters for agents specifically. git will refuse to have the same branch checked out in two worktrees at once — that's the whole safety property. Give each worker agent its own branch and its own worktree directory, and two agents physically cannot stomp on each other's uncommitted changes, even if they're both editing the same file in the same repo. That guarantee is what makes "isolation" in this track a fact about the filesystem, not a promise an agent has to keep.

Check your grip before you build

What's the one-sentence difference between a worktree and a clone?

A clone duplicates the entire .git object store onto disk again; a worktree is a second working directory that shares the same .git object store as the original checkout — one history, multiple rooms.

You try to check the same branch out in two worktrees at once. What happens?

Git refuses. A branch can only be checked out in one worktree at a time — this is exactly the safety property that lets two agents work in parallel without physically colliding. Each worker needs its own branch.

Your turn — stand up a practice repo and a worktree

This is also where the practice repo for the rest of this track gets born. Pick a name and a location outside rabbitmq-microservice-demo — a sibling directory works well, e.g. ~/agent-pipeline-practice. You create it; I'm not touching it for you.

Step 1 — a tiny repo to practice on

Initialize a fresh git repo. Add one trivial file (a README.md is fine) and commit it on main. This is the repo you'll keep reusing for the rest of the track, so a real name beats test123. 

# in the parent directory where you want it
mkdir agent-pipeline-practice && cd agent-pipeline-practice
git init
# create README.md, then:
git add README.md
git commit -m "init"

Step 2 — add a linked worktree

Create a new branch and a new worktree for it in one command, in a directory next to (not inside) your main checkout. Read git worktree add --help for the exact flag to create the branch in the same step — don't just copy a command, know what each piece does before you run it. 

# from inside agent-pipeline-practice/
git worktree add ../agent-pipeline-practice-feature -b feature/hello

Notice the new directory is a sibling of your main checkout, not nested inside it — nesting a worktree inside the repo it belongs to is a common early mistake and confuses git's own status output.

Step 3 — prove the two worktrees share history

cd into the new worktree, make a small edit, and commit it there — on feature/hello, not main. Then go back to your original directory and run git log --oneline --all --graph. You should see both commits, on both branches, from either worktree — because there's only one .git behind them. Also run git worktree list from either directory and read what it shows you.

Step 4 — clean up

Remove the linked worktree (not the branch — decide separately whether you want to keep feature/hello or delete it too). Figure out the command yourself from git worktree --help before you run it.

Verify it yourself: after Step 4, git worktree list should show only your main checkout again, but git log --all should still show the commit you made in the feature worktree (unless you also deleted the branch) — proof the history lived in the shared object store the whole time, not in the worktree directory you just removed.
