Lesson 2 — Hand the work to someone else

Claude Code subagents: bounded delegation with an independent context window.

Lesson 1 gave a worker its own room (a worktree). This lesson gives it its own head — a subagent: a separate Claude Code invocation with its own system prompt, its own tool access, and critically, its own context window. That last part is the whole point. Every tool call a subagent makes — every file it reads, every command it runs — happens in its context, not yours. Only the final report comes back. This is the mechanic that makes "prompt → work → prompt → work" stop being the only shape a session can take: instead of you personally reading 400 lines of git log to summarize them, something else does the reading and hands you the summary.

By the end you'll have written a real subagent definition, watched Claude Code delegate to it, and proven — not just read about — that its raw tool output never touched your main conversation's context. That proof is the thing Lesson 3 builds on: a worker agent inside a worktree is this same isolation, applied to actual code changes instead of a summary task.

The one idea that trips everyone up

A subagent is not a different, smarter model, and it isn't "the same conversation, politely asking a favor." It's a fresh session: a markdown file (YAML frontmatter + a system-prompt body) that Claude Code can spin up on demand, hand a self-contained task to, and read a report back from. It doesn't see your conversation history unless you put it in the prompt you hand it. That's a feature, not a limitation — statelessness is exactly what keeps its context clean for the one bounded thing it's doing.

— Claude Code docs: subagents are used "when a side task would flood your main conversation with search results, logs, or file contents you won't reference again." See Create custom subagents.

Two ways a subagent gets used. (1) Automatic — Claude reads its description field and decides, based on your request, that this subagent fits, then delegates on its own. (2) Explicit — you (or a planning agent) name it directly: "use the repo-summarizer agent for this." This track will use both: automatic for convenience, explicit once orchestrate-prd is doing deliberate wave planning and needs a specific worker for a specific slice.

Check your grip before you build

What's the single thing a subagent has that makes delegation worth it?

Its own context window. Whatever it reads or runs stays in its context; only the final report crosses back into yours — so your own context doesn't fill up with detail you'll never need again.

A subagent definition file has two parts. What are they?

YAML frontmatter (name, description, allowed tools, optionally which model) and a markdown body that becomes the subagent's system prompt.

Can a subagent see the conversation history that led up to it being called?

No — it starts fresh. It only knows what's in the task description/prompt handed to it. Anything it needs from prior context has to be spelled out explicitly when it's invoked.

Step 1 — a bounded, read-only subagent

Create .claude/agents/repo-summarizer.md. Give it frontmatter with a name, a description specific enough that Claude Code will recognize when to delegate to it (vague descriptions don't trigger reliably — be concrete about what kind of request it handles), and a narrow tools list — this agent only needs to read, not write. The body is its system prompt: tell it what to look at (recent commits, current worktrees, working tree status) and what shape to report back in (short — a few bullet points, not a transcript). 

---
name: repo-summarizer
description: >
  Use to summarize the current state of a git repo -- recent commits,
  active worktrees, and working tree status -- as a short report.
tools: Bash, Read
---

Keep the tools list to what the job actually needs. A read-only subagent that can't run git commit is a small, cheap safety property — the same instinct behind Lesson 5's "reviewer with no stake in the implementation."

Step 2 — trigger it, and watch what happens

Ask your main session something that matches the subagent's description — phrase it the way a real request would come in, not by naming the agent. Confirm Claude Code actually delegates (it'll usually say so, or you'll see the Agent tool invoked) rather than answering directly itself.

Step 3 — prove the isolation, don't just trust it

Immediately after the subagent reports back, ask your main session a follow-up that can only be answered from the raw git log output (something specific the summary almost certainly left out — an exact commit hash, or the full message of a commit that didn't make the summary). If the isolation is real, the main session won't know it — it only received the condensed report, not the subagent's tool output.

Verify it yourself: Step 3 either fails informatively (the main session says it doesn't have that detail, or has to re-run the command itself to find out) or it answers instantly because the detail happened to be in the summary. Either outcome teaches you something concrete about what crosses the boundary and what doesn't — that's the real lesson, more than the delegation itself.
