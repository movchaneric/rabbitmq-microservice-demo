Lesson 3 — A worker with its own room and its own head

Composing Lessons 1 and 2: a subagent that writes code inside a worktree Claude Code stages for it.

Lesson 1 gave you a room by hand (git worktree add). Lesson 2 gave you a head with its own context (a subagent). This lesson stops doing either by hand: add one line to a subagent's frontmatter, and Claude Code stages the worktree for it — creates it before the subagent touches a file, and actively blocks that subagent from writing anywhere outside it. This is the literal mechanic behind "worker agents in isolated git worktrees" — not a convention worker agents are supposed to follow, a thing Claude Code enforces whether they try to follow it or not.

By the end you'll have a subagent that makes a real file change inside a worktree it never had to set up itself, you'll have watched your main checkout stay untouched while that happened, and you'll have merged the result back by hand. That manual merge is exactly the step Lesson 6's risk-tiered gate will later decide whether to automate or block.

The one idea that trips everyone up

"Isolated" here isn't a suggestion in the subagent's system prompt — it's enforced by Claude Code itself, the same way a database transaction is enforced by the database, not by the application remembering to be careful. Once a subagent (or session) is running inside a worktree, Claude Code actively blocks three categories of tool call from reaching the main checkout: file edits (Edit/Write) targeting a main-checkout path, any command whose working directory resolves there, and any git command that redirects into it (git -C, --git-dir, a cd before running git). A worker agent physically cannot step outside its room, even if its prompt tried to make it.

Cleanup is conditional, and that's a feature. A subagent's worktree is removed automatically only if it finishes with no changes. If it made changes, the worktree stays on disk — Claude Code won't quietly discard work just because the subagent that produced it exited. A periodic sweep (governed by the cleanupPeriodDays setting) later removes worktrees that are old and have nothing uncommitted, nothing untracked, and nothing unpushed. Anything with live work in it is safe from the sweep too.

Check your grip before you build

How do you make worktree isolation permanent for one named subagent, not just this session?

Add isolation: worktree to that subagent's YAML frontmatter. Every time it runs, from any session, Claude Code stages a worktree for it first.

When does Claude Code auto-remove a subagent's worktree right after it finishes?

Only when the subagent finished having made no changes. If it changed anything, the worktree — and the work in it — stays on disk until you deal with it (or the periodic sweep does, once it's old and fully clean).

Name the three categories of tool call Claude Code actively blocks from reaching the main checkout.

File edits (Edit/Write/NotebookEdit) targeting a main-checkout path; a Bash/PowerShell command whose working directory resolves to the main checkout; and a git command redirected into the main checkout (-C, --git-dir, a cd first, etc).

Your turn — a worker that writes for real

Back in /Users/ericmovchan/agent-pipeline-practice. This time the subagent writes something, so worktree isolation actually has something to protect.

Step 1 — a worker subagent, isolated by default

Create .claude/agents/scaffolder.md: give it a description for a small, well-defined writing task (e.g. "adds a dated entry to CHANGELOG.md summarizing a described change" — keep the scope tiny and unambiguous, this is about the isolation mechanic, not the task itself), a tools list that includes Write or Edit, and — the new part — isolation: worktree in the frontmatter.

Step 2 — delegate to it, then check your main checkout first

Trigger the subagent with a real, small task matching its description. Before you look at its report, run git status and git worktree list in your main checkout. Confirm: your working tree is still clean, and a new worktree now exists that you didn't create by hand.

Step 3 — inspect, then merge it back

cd into the worktree Claude Code created and look at what the subagent actually wrote (git log, git diff against the base branch). If it's what you expect, merge it into your main checkout the plain way — decide for yourself whether that's a fast-forward merge, a regular merge commit, or something else, and be able to say why. This manual "does it look right, then I merge it" step is exactly what Lesson 6 will formalize into a gate instead of a judgment call.

Step 4 — clean up

Remove the worktree once you've merged (or discarded) its work — same git worktree remove muscle from Lesson 1, now on a worktree you didn't create yourself.

Verify it yourself: at every point before Step 3's merge, your main checkout's git status should read clean — no trace of the subagent's work until you deliberately pull it in. That gap between "the work exists" and "the work is in your checkout" is the whole isolation guarantee, made visible.

Where this points next

You now have the two mechanical pieces the mission names explicitly: worker agents, in isolated git worktrees. What's still missing is everything upstream and downstream of one worker — who decides what work to hand out and in what order (Lesson 4's planning agent and wave planning), and who checks a worker's output before it's allowed to merge (Lesson 5's independent review). Lesson 3 was "can one worker be trusted with a room of its own"; Lessons 4–6 are "how do many of them get coordinated."
