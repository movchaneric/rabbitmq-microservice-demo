Lesson 4 — Someone has to decide who works on what, and when

The planning agent: decomposing a body of work into waves of independent, parallel-safe slices.

Lessons 1–3 built one worker: a subagent, isolated in its own worktree, that can be trusted with a piece of work. That's necessary but not sufficient — nothing yet decides what piece of work each worker gets, or whether two workers running right now are safe to run at the same time. That's the planning agent's job: read a body of work, break it into independent slices, and group those slices into waves — batches where everything in a wave can run in parallel, and each wave only starts once the wave before it is done.

By the end you'll have manually planned a real wave (2–3 independent slices), dispatched all of them in parallel in one turn using what you built in Lesson 3, and merged the results back — while also proving to yourself the one thing worktree isolation quietly does not protect you from.

The one idea that trips everyone up

Worktree isolation stops two workers from clobbering each other's uncommitted, in-progress work — that part is enforced by Claude Code itself, as you saw in Lesson 3. It does nothing to stop a merge conflict once both workers finish and you try to bring their separate, committed branches back into one checkout. If worker A and worker B both edited the same file, you get a completely ordinary git merge conflict — worktrees never touched that problem, because by the time it happens, isolation has already done its job and stepped aside.

So what makes two slices safe to put in the same wave? Two conditions, both necessary: (1) no dependency — neither slice needs the other's output to be correct or even to make sense, and (2) no file/module overlap — ideally they don't touch the same files at all. Condition 1 is about correctness. Condition 2 is about avoiding busywork merge conflicts on the way back in. A planning agent that only checks dependency and ignores overlap will still "work," but every wave becomes a conflict- resolution chore.

Check your grip before you build

What does worktree isolation protect against, and what does it explicitly NOT protect against?

It protects against two workers colliding on the same live, uncommitted files at the same time. It does not protect against an ordinary merge conflict once both workers' finished, committed branches get merged back — that's a plain git problem, unrelated to isolation.

Name both conditions that make two slices safe to run in the same wave.

No dependency (neither needs the other's output), and no file/module overlap (so merging both back doesn't produce a conflict even though they ran in parallel).

Mechanically, in Claude Code, how do you actually run "a wave" of several workers at once?

Call multiple Agent/Task invocations in the same turn/message. Calling them one at a time, waiting for each before starting the next, is sequential — not a wave, no matter how independent the work is.

Your turn — plan and run a real wave

Back in /Users/ericmovchan/agent-pipeline-practice. This time you are the planning agent, doing the decomposition by hand before handing anything to Claude Code.

Step 1 — pick 2–3 genuinely independent slices

Choose two or three small pieces of work that satisfy both conditions above: no dependency, no file overlap. Something like "add a CONTRIBUTING.md", "add a .gitignore", and "add a short LICENSE" works well — three different files, none needs the others to exist first. Write down, in your own words, why each pair is safe to run together. If you can't justify it, you haven't planned the wave — you've guessed.

Step 2 — dispatch the wave in parallel

Using your Lesson-3 worker subagent (or a variant of it — reuse isolation: worktree), delegate all the slices in one turn — one message, multiple worker invocations, no waiting between them. Watch for confirmation that they actually ran concurrently rather than one after another.

Step 3 — merge the wave back, one slice at a time

Merge each worker's branch into your main checkout in turn. Because you planned for no file overlap, this should go cleanly — no conflicts. If you do hit one, that's a real signal your slicing missed something; don't just resolve it and move on without figuring out which condition (dependency or overlap) you actually violated.

Step 4 — break it on purpose

Now do it wrong, deliberately: plan a "wave" where two slices touch the same file (e.g. both told to add a line to the same README.md, in different places). Dispatch them in parallel the same way, then try to merge both back. You should hit a real merge conflict. This is the cheapest, safest place to feel that failure mode — better here than inside orchestrate-prd later.

Verify it yourself: Step 3's wave merges with zero conflicts; Step 4's doesn't. If both went cleanly, your Step 4 slices weren't actually overlapping — go make them collide for real. The failure is the point of the exercise, not something to avoid.

Where this points next

You can now plan and run one wave. What's still missing: nothing has independently checked whether a worker's output is actually correct before it merges — you did that judgment call yourself in Steps 3–4. Lesson 5 hands that job to a reviewer agent with no stake in the implementation, and Lesson 6 turns "looks right, merge it" into an explicit, risk-tiered gate instead of a vibe check.
