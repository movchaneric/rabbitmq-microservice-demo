Every check you've ever done on this code — does it build, does it work — you did by hand, by running it yourself. CI and CD are two different things

It's easy to say "CI/CD" as one word. They're not one thing, and conflating them is a common source of confusion once a pipeline has both:

  • CI (Continuous Integration) answers: does this change actually work? Every push, every PR, automatically build it and run its tests. CI's job ends there — it doesn't put anything anywhere.
  • CD (Continuous Deployment) answers: should this change go live, and did it? It only makes sense to run after CI has already said yes. A workflow can run CI on every branch, but only run CD when the branch is main and CI succeeded.

This lesson is entirely CI. CD (deploying to Render) comes once every service already has a real, trustworthy CI gate — there's nothing worth auto-deploying yet, because nothing is verified yet.

The concept: anatomy of a GitHub Actions workflow

A workflow is a YAML file in .github/workflows/. GitHub watches for an event (a push, a pull_request, etc.) and, when one matches, runs the workflow. A workflow contains one or more jobs; each job runs on its own fresh, single-use runner (a VM GitHub spins up and throws away when the job ends — declared via runs-on: ubuntu-latest). Inside a job, steps run in order on that same machine: a step is either a plain shell command (run:) or a call to a packaged, reusable action someone else wrote (uses: actions/checkout@v4).

Why "fresh runner" matters: every job starts from a blank machine — no repo checked out, no dependencies installed, nothing left over from the last run. That's why the very first step in almost every job is actions/checkout (get the repo's code onto this machine at all) — CI isn't running against your local filesystem, it's running against a clean checkout of exactly what you pushed.

Primary source — read this before the exercise: GitHub Docs — Understanding GitHub Actions. Full annotated example: this workspace's own cheat sheet.

Check your understanding

Three short-answer questions, one word each. Type an answer, hit Check, then compare.

Q1. What's the smallest unit inside a job — a single shell command or action call?

Expected: "step" — steps in a job run in order, on the same runner, sharing its filesystem (so a later step can see files an earlier step created).

Q2. What's the general term for the thing that causes a workflow to start running at all (push, pull_request, schedule, ...)?

Expected: "event" — declared under a workflow's on: key. No matching event, no run — not even a skipped one, it just never triggers.

Q3. What do you call a reusable, packaged step someone else wrote and published, that you reference with `uses:` instead of hand-writing the equivalent shell commands?

Expected: "action" — e.g. actions/checkout, actions/setup-node. This is also the "Actions" in "GitHub Actions": the whole system is named after this building block.

Before the exercise: there's nothing to test yet

order-service has zero tests. A CI workflow that runs zero tests is a green checkmark that means nothing — so before writing any YAML, you're writing one real test. The test target: order-service/src/data.ts, which already exists and has no I/O (no RabbitMQ, no Redis, no HTTP) — the cleanest possible thing to unit-test first. 

// order-service/src/data.ts (already exists, unchanged)
export function addOrder(order: Order): void {
  orders.push(order);
}

export function getOrders(): Order[] {
  return orders;
}

Test framework choice: Vitest. It's TypeScript-native (no separate `ts-jest` config step), fast, and has become the default choice for new TypeScript projects — a reasonable professional default without pulling in Jest's extra configuration surface for a project this size.

The exercise

Three files. Blanks (___) are yours to fill using the concepts above.

1. order-service/package.json

Add Vitest as a dev dependency and a test script:

npm install --save-dev vitest --prefix order-service

Then add this to the "scripts" object:

"test": "___"

What command actually runs Vitest's test suite once (not in watch mode)? Check Vitest's own CLI docs if unsure, or ask me.

2. order-service/src/data.test.ts (new file)

A real test — not a placeholder. It needs to prove two things: an order you add comes back out of getOrders(), and it comes back with the same orderId you put in.

import { describe, it, expect } from "vitest";
import { addOrder, getOrders } from "./data";

describe("data", () => {
  it("___", () => {
    const order = {
      orderId: "___",
      productId: "sku-1",
      quantity: 1,
      customerEmail: "test@example.com",
      timestamp: new Date().toISOString(),
    };

    ___(order);

    const orders = ___();
    expect(orders).___(
      expect.objectContaining({ orderId: "___" })
    );
  });
});

The first blank is the test's description string (say what it's checking, not just "test 1"). The matcher blank is a Vitest/Jest array assertion — one exists specifically for "does this array contain an object matching this shape." Ask me if you can't find it.

3. .github/workflows/order-service-ci.yml (new file, repo root)

Use the annotated skeleton in the reference cheat sheet as your model. Requirements, not exact syntax — work out the YAML yourself:

  • Name it something recognizable in the Actions tab.
  • Triggers on push and pull_request, but only when files under order-service/ actually changed (this is the path filter — there's no reason to run this workflow because someone edited gateway/).
  • One job, on the standard Ubuntu runner.
  • Steps, in order: check out the repo, set up Node (pick a version — check order-service/package.json's devDependencies for a hint of what this repo already assumes), install dependencies with npm ci (not npm install — ask me why if you don't already know), run the test script.
  • All commands need to run from order-service/, not the repo root — the reference sheet shows the YAML key for that.

Verify it works

  1. Run the test locally first, before ever pushing: npm test --prefix order-service. It should pass.
  2. Commit and push your branch (or open a PR) and watch the Actions tab on GitHub — you should see a run start within a few seconds.
  3. Deliberately break it: comment out the addOrder(order); line in your test's arrange step (not the real data.ts), push again, and confirm the workflow run actually turns red. A CI check that can't fail isn't testing anything.
  4. Undo the deliberate break, push again, confirm it's green.
  5. Edit a file in a different service (e.g. add a comment in gateway/src/index.ts), push, and confirm this workflow does not run at all — that's the path filter working.
order-service now has a real, automated check that runs on every push and PR, fails when the code is actually broken, and stays out of the way when unrelated services change. This is the exact shape every other service's CI will follow.
