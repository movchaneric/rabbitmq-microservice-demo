CI/CD Lesson 5: CD — Deploying to Render via a Deploy Hook

Tied to mission: turn a green CI run into an actual, reachable, deployed order-service

Where you are

Every push to main under order-service/** already produces a real, SHA-tagged image sitting in GHCR (Lessons 1-4). Nothing has ever pulled that image and run it anywhere reachable — it just accumulates in the registry. This lesson closes that gap for one service: order-service gets a real Render Web Service, and CI calls a deploy hook to tell Render "a new image just landed, go run it" — automatically, only after CI has actually passed on main. The other 4 services stay exactly as they are for now; scaling this to all 5 is its own later lesson, same shape as Lessons 3→4.

The concept: CD is a second event, not a continuation of CI

CI answered "is this commit good?" CD answers a completely different question: "should what's currently deployed be replaced with this commit?" Those are separate concerns with separate triggers, even though CD should never fire unless CI already said yes.

A deploy hook is a unique, secret URL Render generates per service. Sending it an empty POST request tells Render "pull whatever image is currently tagged for this service and redeploy it" — no auth header, no payload, the URL itself is the credential. That's exactly why it's a GitHub Actions secret, never a plain workflow input: anyone who has that URL can trigger a deploy of your service, unprompted.

Render doesn't build your code itself here — push-image (Lesson 3) already built and pushed the image to GHCR. Render's job is narrower: pull that specific image and run it as a container. That split — GitHub Actions builds, GHCR stores, Render runs — is why the deploy hook call only needs to happen after push-image has actually succeeded; calling it any earlier would tell Render to redeploy before there's anything new to pull.

Why gate on `push` to `main`, not `pull_request`, again? Same CI-vs-CD boundary from Lesson 3: a PR's `push-image` job doesn't even run (recall its `if:` condition), so there is no image from a PR commit for a deploy hook to point at in the first place. Deploys only ever follow a merge to `main`.

Primary source — read this before the exercise: Render Docs — Deploy Hooks.

Manual setup (do this in the Render/CloudAMQP dashboards, not in this repo)

This part isn't a code exercise — there's no blank to fill in a browser. Do these in order, then come back for the workflow change:

  1. CloudAMQP: create a free "Little Lemur" instance. Copy its AMQP URL (CloudAMQP — Getting Started) — this is what order-service's code already reads as process.env.RABBITMQ_URL (see services/order-service/src/rabbitmq/connection.ts). It's the same env var name your local docker-compose.yml already uses, just pointed at a hosted broker instead of your local cluster.
  2. Render Key Value: create a free Key Value instance from the Render dashboard. Copy its connection string — this is REDIS_URL (services/order-service/src/redis/client.ts throws at import time if it's missing, so this one's non-optional).
  3. Render Web Service: create a new Web Service, choose "Existing Image" as the deploy type (not "build from repo" — CI already builds it), and point it at ghcr.io/<your-github-username>/order-service:<some-sha-that's-already-in-GHCR> as the initial image. Set its environment variables: PORT (Render sets this one itself, don't override it), RABBITMQ_URL, REDIS_URL from the two steps above.
  4. Once the service exists, go to its Settings → Deploy Hook and copy the URL. In this GitHub repo, go to Settings → Secrets and variables → Actions and add it as a new repository secret named RENDER_DEPLOY_HOOK_ORDER_SERVICE.
If GHCR's package is currently private, Render won't be able to pull it without credentials of its own — check the package's visibility under your GitHub profile's Packages tab first (public is fine for this learning repo; a real company would instead give Render a scoped pull token).

Check your understanding

Three short-answer questions, one word each.

Q1. The deploy hook URL is the credential itself — anyone with it can trigger a deploy. What GitHub Actions mechanism is it stored as, so it's usable in a workflow but never visible in logs or committed to the repo?

Expected: "secret" — a repository (or environment) secret, referenced as secrets.RENDER_DEPLOY_HOOK_ORDER_SERVICE. Same mechanism as GITHUB_TOKEN in Lesson 3, but one you create yourself instead of one GitHub issues automatically.

Q2. What job-level YAML key makes the deploy job wait for `push-image` to actually finish successfully first, instead of starting immediately when the workflow triggers?

Expected: "needs" — needs: push-image. Without it, the deploy job would run in parallel with (or even before) the image build finishes, telling Render to redeploy an image that doesn't exist yet.

Q3. When the deploy hook fires, what verb describes the action Render itself takes against GHCR to get the new image — the same verb that's the opposite of what `push-image` did in Lesson 3?

Expected: "pull" — Render pulls the image; CI pushed it. Two separate systems, two separate directions, connected only by the registry sitting between them.

The exercise

Two small changes. Blanks (___) are yours to fill.

.github/workflows/service-ci.yml — add a new job

  deploy:
    needs: ___                                          # from Q2 — which job must succeed first?
    if: github.event_name == 'push' && github.ref == 'refs/heads/main' && inputs.service == '___'   # scoped to one service only, for now
    runs-on: ubuntu-latest
    steps:
      - run: curl -X ___ "${{ secrets.deploy_hook }}"    # what HTTP verb does hitting a deploy hook use? (see Lesson 3, Q1's neighbor concept)

Note the new job reads secrets.deploy_hook — a name that doesn't exist yet anywhere. That's because reusable workflows don't automatically receive the caller's secrets; they have to be explicitly declared and passed, the same way inputs.service is explicitly declared and passed. Ask me about the on: workflow_call: secrets: block if you're not sure how to declare one.

.github/workflows/ci.yml — pass the secret, order-service only

  order-service:
    needs: changes
    if: needs.changes.outputs.order-service == 'true'
    permissions:
      contents: read
      packages: write
    uses: ./.github/workflows/service-ci.yml
    with:
      service: order-service
      path: services/order-service
    secrets:
      deploy_hook: ${{ secrets.___ }}                    # the repository secret name you created in the manual setup

Notice the other 4 services' caller jobs don't get a secrets: block at all — that's deliberate, not an oversight. Their deploy job in service-ci.yml will still evaluate its if:, see inputs.service != 'order-service', and simply not run. Nothing breaks for the other 4; they just don't have anywhere to deploy to yet.

Verify it works

  1. Push a real change under order-service/** to main.
  2. In the Actions tab, confirm you now see three nested jobs run in order: test → push-image → deploy.
  3. In the Render dashboard, open your Web Service's Events tab — confirm a new deploy started right around when the deploy job ran, and watch it go live.
  4. Hit the deployed service's public URL (Render gives you one, e.g. https://order-service-xxxx.onrender.com) and confirm it actually responds — this proves RABBITMQ_URL and REDIS_URL were wired correctly, not just that a container started.
  5. Push a change under a different service (e.g. gateway/) and confirm no deploy job runs at all for it — order-service's job doesn't even appear in that run, same path-filter behavior as Lesson 4.
A push to main now travels all the way from your laptop to a real, publicly reachable server, with no manual step in between — and only after a real test suite has actually passed. That's the whole point of CI/CD: the pipeline is the only path to production, not a convenience next to a manual one.
