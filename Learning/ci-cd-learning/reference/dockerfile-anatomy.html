Reference: Anatomy of a Multi-Stage Dockerfile

Quick-reference cheat sheet — see Lesson 2 for the taught version

Annotated skeleton

# ---- builder stage ----
FROM node:20-alpine AS builder     # base image; "AS builder" names this stage
WORKDIR /app                       # every instruction below runs from here, inside the image

COPY package*.json ./              # copy ONLY manifest files first
RUN npm ci                         # install deps — cached as long as package*.json is unchanged

COPY . .                           # now copy the rest of the source
RUN npm run build                  # compile TypeScript -> dist/ (tsconfig's outDir)

# ---- runtime stage ----
FROM node:20-alpine                # a FRESH base image — none of the builder's layers carry over
WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev              # only production deps — no typescript, no ts-node, no vitest

COPY --from=builder /app/dist ./dist   # pull ONLY the compiled output out of the builder stage

EXPOSE 3001                        # documentation only — doesn't publish the port by itself
CMD ["node", "dist/index.js"]      # plain node, running compiled JS — no ts-node in the final image

Why two stages instead of one

A single-stage build would need the TypeScript compiler, ts-node, and every dev dependency present in the image you ship — none of which the running app ever uses. Multi-stage builds let an early stage carry all of that, then throw the entire stage away except the one folder (dist/) the final stage actually needs. Source: Docker Docs — Multi-stage builds.

Key instructions

InstructionDoes
FROM <image> AS <name>Starts a new stage from a base image; AS name makes it referenceable later
WORKDIRSets the working directory inside the image for every instruction after it
COPY <src> <dest>Copies files from the build context (host) into the image
COPY --from=<stage> <src> <dest>Copies files from an earlier stage's filesystem instead of the host
RUNExecutes a command while building — its filesystem effects become a layer
EXPOSEDocuments which port the container listens on — you still map it yourself with docker run -p
CMDThe default command that runs when a container starts from this image

.dockerignore

Same idea as .gitignore, but for what Docker is allowed to COPY from the build context. At minimum: 

node_modules
.env
dist

Excluding node_modules matters beyond just speed: your host's node_modules may contain platform-specific native binaries (macOS) that would silently break inside the Linux-based image — the exact class of problem you already hit with the CI lock file in Lesson 1, just one layer further down the stack.

Useful build/run commands

docker build -t order-service:local .          # build, tag it locally
docker images order-service:local              # check the actual final size
docker run --rm -p 3001:3001 \
  --network <compose-network> \
  -e PORT=3001 \
  -e RABBITMQ_URL=amqp://guest:guest@haproxy:5672 \
  -e REDIS_URL=redis://redis:6379 \
  order-service:local
docker network ls                              # find the compose-created network's real name
