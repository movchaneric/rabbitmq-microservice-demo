Reference: Anatomy of a GitHub Actions Workflow

Quick-reference cheat sheet — not a lesson, see Lesson 1 for that

The file

Lives at .github/workflows/<anything>.yml, anywhere in the repo the workflow applies to. GitHub scans every file in that folder — the filename itself doesn't matter to GitHub, only to humans reading the Actions tab.

Annotated skeleton

name: order-service CI                    # label shown in the Actions tab

on:                                        # the EVENT(s) that start a run
  push:
    branches: [main]
    paths: ["order-service/**"]            # path filter — skip if nothing here changed
  pull_request:
    paths: ["order-service/**"]

jobs:                                      # one workflow -> one or more JOBS
  test:                                    # job id (your name for it)
    runs-on: ubuntu-latest                 # the RUNNER — a fresh VM, thrown away after
    defaults:
      run:
        working-directory: order-service   # every `run:` step below executes from here

    steps:                                 # STEPS run in order, same machine, same filesystem
      - uses: actions/checkout@v4          # ACTION: reusable, packaged step someone else wrote
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
      - run: npm ci                        # plain shell command instead of an action
      - run: npm test

Two events you'll use constantly

EventFires onTypical use
pushA commit lands on a branch (e.g. after a PR merges to main)CI on main, or trigger CD
pull_requestA PR is opened/updatedCI gate before merge — this is what actually blocks a bad merge

Job dependencies

jobs:
  test:
    runs-on: ubuntu-latest
    steps: [ ... ]

  build:
    needs: test              # waits for `test` to succeed before starting
    runs-on: ubuntu-latest
    steps: [ ... ]

Without needs:, jobs in the same workflow run in parallel by default — fine for independent work, wrong if build should only happen after test actually passes.

Secrets, at a glance

steps:
  - run: curl -X POST ${{ secrets.RENDER_DEPLOY_HOOK_URL }}

Set once in Settings → Secrets and variables → Actions (repo-level) or on a specific Environment (scoped further, can require reviewers). Never appears in the YAML itself, and GitHub automatically masks a secret's value in logs if it's ever echoed.
