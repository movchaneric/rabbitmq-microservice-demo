Lesson 1 — Close the front door

API-key authentication: identify the caller before anything else runs.

Right now every route on your gateway is wide open. Anyone who can reach localhost:3000 can place orders, flip inventory into failure mode, or read the dead-letter queue. An enterprise gateway's first job is to decide who is calling before a request touches a backend. This lesson adds the simplest form of that gate — an API key — and sets up everything the next lesson needs to meter each caller individually.

By the end, a request with no key (or a bad key) gets a 401 and never reaches a backend. A request with a valid key sails through and arrives at your rate limiter carrying the caller's identity — the hook Lesson 2 turns into per-caller usage plans.

The one idea that trips everyone up

An API key is not authentication. It identifies which application is calling so you can meter and throttle it — it does not prove the caller is who they say they are. AWS says this in bold in their own docs:

"Don't use API keys for authentication or authorization to control access to your APIs … API keys shouldn't include confidential information; clients typically transmit them in headers that can be logged."

— AWS, Usage plans and API keys for REST APIs

That is exactly why you chose "both, in sequence." The API key answers "which app is this?" (metering, tiers, quotas). Later, JWT will answer "which user is this, and can I trust it?" (real authentication). Today we build the first one — and we're honest about what it is.

ConcernQuestion it answersTool
Identification / meteringWhich app is calling?API key (this lesson)
AuthenticationIs this really that user?JWT (Phase B)
AuthorizationMay this caller do this?Scopes / roles (later)

How AWS models it (our reference design)

  • The client sends the key in a header. AWS's default header name is x-api-key — we'll use the same, so your gateway speaks the same dialect as a real one.
  • The gateway looks the key up in a registry. A hit maps the key to an identity (an app name, and — next lesson — a usage plan). A miss is rejected.
  • A missing/unknown key is rejected before routing, throttling, or validation — auth is the outermost layer.
401 vs 403 — pick the right one. 401 Unauthorized means "I don't know who you are" — no key, or a key I don't recognize. That's this lesson. 403 Forbidden means "I know who you are, but you're not allowed to do this" — that's an authorization decision for later. A 401 should carry a WWW-Authenticate header naming the scheme. See the glossary.

Check your grip before you build

Which request header does AWS API Gateway use by default for the API key?

x-api-key. Using the same name means clients written against a real AWS gateway would work against yours unchanged.

A caller sends a key you don't recognize. 401 or 403 — and why?

401. An unknown key means you can't identify the caller at all — "I don't know who you are." 403 is for a caller you have identified but who isn't permitted to do the thing they asked.

In one sentence: why is a valid API key not proof of authentication?

Because the key only says which application is calling (for metering/throttling) — it travels in a loggable header and anyone who copies it can present it. It doesn't verify the caller's identity the way a signed token does.

Step 1 — a key registry

Create gateway/src/auth/apiKeyRegistry.ts. For this lesson the registry is a plain in-memory map: apiKey → { appName, plan }, seeded from an env var (e.g. API_KEYS) so keys aren't hard-coded in source. Export a lookup(key) that returns the identity or undefined.

Why in-memory now? It keeps this lesson to one idea. In Lesson 2 the registry moves to Redis — because per-key throttle and quota counters need a store shared across gateway instances, and that migration is itself the lesson. Don't over-build today.

Step 3 — wire it in, outermost

In gateway/src/index.ts, mount apiKeyAuth so it runs before the rate limiters and proxies. Think about scope: should it guard every /api/v1 route, or all of them plus leave a health check open? Which app.use(...) position gives you "auth first, always"?

Verify it yourself (you run these): with the service up, a curl to /api/v1/orders without a key should return 401; the same request with a valid x-api-key should behave exactly as before. That's the whole win: the door is closed to strangers and unchanged for holders of a key.
