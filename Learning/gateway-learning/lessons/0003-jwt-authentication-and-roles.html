Lesson 3 — Now prove it's really you

JWT bearer authentication, plus role-based authorization: customer vs admin.

Lesson 1 was explicit about what an API key isn't: proof of who's calling, only proof of which app is calling. Today you build the real thing. A new service, services/auth-service, becomes your identity provider — it registers users, checks passwords, and issues signed JWTs. The gateway's job changes too: it stops trusting bare identity and starts verifying a signature, then asking a second question it's never been able to ask before — is this specific user allowed to do this?

By the end: POST /api/v1/inventory/toggle-fail and GET /api/v1/dead-letters require a valid JWT and the admin role. A customer's token gets a 403. No token, an expired token, or a token with a tampered signature gets a 401. Ordinary routes (placing an order, reading inventory) work for any authenticated user, customer or admin.

Three questions, three mechanisms — now all three exist

ConcernQuestion it answersTool
Identification / meteringWhich app is calling?API key (Lesson 1)
AuthenticationIs this really that user?JWT — today
AuthorizationMay this user do this?Role check — today

Notice all three can be true at once on one request: a mobile app (API key) calling on behalf of a logged-in customer (JWT) who is trying to place an order they're allowed to place (role check passes). A real gateway runs all three checks, in that order, on every request that needs them.

Where the token comes from

The gateway will never mint a JWT — only verify one. That job belongs to services/auth-service, a small new service with two routes: POST /register (hash a password, store a user with a role) and POST /login (check the password, sign a JWT). This is the same shape as a real identity provider — Cognito, Auth0, Keycloak — sitting outside the gateway. The gateway's authorizer only ever answers "is this signature valid, and is it still fresh?" — it never touches a password.

The simplification we're making, on purpose. Today, auth-service and the gateway share one secret (JWT_SECRET, HS256) — both sides know it, because you control both services. A real external IdP doesn't share a secret with you at all: it signs with a private key and publishes only the public key (via a JWKS endpoint), so anyone can verify but only the IdP can sign. That's asymmetric trust, and it's exactly what Phase C (real OAuth2) replaces this with. For now, the shared secret keeps today's lesson to one new idea — verification and roles — instead of two.

Anatomy of the token you're about to mint

A JWT is three base64url segments joined by dots: header.payload.signature. The payload is a bag of claims — plain JSON, readable by anyone, so never put a secret in it. The signature is what makes it trustworthy: it proves the payload hasn't been altered since the issuer signed it. 

// what auth-service will put in the payload
{
  "sub": "alice@example.com",   // registered claim: subject — who this token is about
  "role": "customer",           // custom claim — yours, not part of the JWT spec
  "iss": "gateway-demo-auth",   // registered claim: issuer — who signed this
  "aud": "gateway-demo-api",    // registered claim: audience — who this token is for
  "iat": 1753776000,            // issued-at
  "exp": 1753776900             // expiry — 15 minutes later
}

Claim names and meanings: RFC 7519 §4.1. Plain-language walkthrough: jwt.io — Introduction to JSON Web Tokens.

The mistake that breaks JWT security. A verifier must decide in advance which algorithm and which secret/key to check a signature against — never read alg out of the token and use whatever it says. If you did, an attacker could hand you a token with alg: none (no signature to check at all) and you'd accept it. This is real enough to have a name — the alg confusion attack. The fix is one line: pass algorithms: [...] explicitly to jwt.verify. See the OWASP JWT Cheat Sheet, which also covers checking exp/iat/nbf and iss/aud — all of which jwt.verify does for you, but only for the options you pass in.

Check your grip before you build

A request has a perfectly valid, unexpired JWT for a customer — but hits the admin-only toggle-fail route. 401 or 403, and why?

403. The gateway knows exactly who this is — the signature checked out. The problem isn't identity, it's permission. 401 is reserved for "I can't tell who you are" (missing, malformed, expired, or forged token).

In one sentence: what does a verifier that trusts the token's own alg field expose it to?

An attacker can hand it a token declaring alg: none (or swap the expected algorithm for one that lets the public key double as an HMAC secret), and the verifier checks nothing — it accepts a token nobody signed.

Why is it safe to trust the role claim inside a JWT for an authorization decision, when it'd be unsafe to trust a role field the client just put in the request body?

Because by the time you read role, you've already verified the signature — the claim can only have the value the issuer put there, since any change would break the signature. A role in a raw request body has no such guarantee; the client could write anything.

Step 6 — wire it in

In gateway/src/index.ts. Two design questions to reason through before you write the line:

Placement of jwtAuthMiddleware. It reads Authorization; apiKeyAuthMiddleware reads x-api-key. They're independent headers checking independent things — which means order between them doesn't change correctness the way, say, auth-before-rate-limiting did in Lesson 1. Where would you put it relative to the existing app.use(apiKeyAuthMiddleware) and app.use(usagePlanQuota) lines, and does it matter?

Which routes get requireRole. Every route should require some logged-in user (mount jwtAuthMiddleware globally, same way apiKeyAuthMiddleware is). Only two routes are admin-only: POST /api/v1/inventory/toggle-fail and GET /api/v1/dead-letters — both operational, neither customer-facing. Everything else (placing orders, reading inventory, reading notifications) should accept requireRole("customer", "admin") — any logged-in user, either role.

Verify it yourself: register one customer and one admin via POST /register on auth-service directly (it's not behind the gateway — it is part of the trust boundary). Log in as each, keep both tokens. As the customer: POST /api/v1/orders → succeeds; POST /api/v1/inventory/toggle-fail → 403. As the admin: same toggle-fail route → 200. No Authorization header at all on any protected route → 401. Then tamper with one character of a valid token and resend it — still 401, because the signature no longer matches.

Where this points next

You now have the full triad — identify, authenticate, authorize — and a real, exercised 401-vs-403 distinction. What's still simulated: the shared secret between auth-service and the gateway, and the fact that auth-service hands back a raw token instead of running a real OAuth2 grant type. Phase C replaces the shared secret with asymmetric signing and teaches the actual protocols production systems use — authorization-code (a human logging in through a browser) and client-credentials (one service calling another, no human involved) — plus refresh tokens, which today's short-lived access token deliberately didn't need yet.
