Lesson 4 — Let a real authorization server issue the tokens

OAuth2 client-credentials grant, backed by a real Keycloak instance you run yourself.

Lesson 1 gave every calling app a static string (x-api-key) you generated and compared with ===. It worked, but you were the entire trust infrastructure — one hardcoded registry, no rotation, no revocation, no real cryptography. Today a real authorization server — Keycloak, running in Docker on your machine — takes that job over. The calling app authenticates itself to Keycloak, gets back a short-lived signed token, and the gateway verifies that token against Keycloak's published public key. No shared secret between the two of them, unlike Lesson 3's auth-service.

By the end: GET /api/v1/dead-letters requires a valid OAuth2 client-credentials token minted by Keycloak — no user, no password, just one service (a monitoring job, in spirit) authenticating as itself. The gateway verifies the token's signature against Keycloak's JWKS endpoint, not a secret it already knows. A tampered or expired token → 401. A token from the wrong client, or missing the expected role → 403.

Why this route, and not every route

Client-credentials tokens represent no human — there's no user to be "customer" or "admin." That's a real conflict with Lesson 3: a request only has one Authorization header, and Lesson 3 already put a user JWT there. Rather than solve "how does the gateway trust two different kinds of bearer token on the same route" in this lesson, we're scoping to a route that was already honestly machine-to-machine: dead-letters. Nobody clicks a browser to check the dead-letter queue — a monitoring job polls it. That's the textbook client-credentials use case, and it means today's code doesn't have to touch jwtAuthMiddleware or requireRole at all. requireRole("admin") on this one route gets replaced, not layered — "role" isn't the right concept for a service account calling on its own behalf.

Multi-issuer trust is a real, separate problem — a production gateway often does need to accept tokens from more than one issuer on the same or different routes (Keycloak for services, your own IdP for users, maybe a partner's IdP too). That's future work once single-issuer JWKS verification exists here. Today is deliberately just one issuer, one route.

The shape of the flow

StepWhoWhat happens
1Calling servicePOSTs its client_id + client_secret to Keycloak's token endpoint
2KeycloakVerifies the client, signs a JWT with its private key, returns it as an access token
3Calling serviceSends Authorization: Bearer <token> to the gateway
4GatewayFetches Keycloak's public key from its JWKS endpoint, verifies the signature — no secret exchanged between gateway and Keycloak, ever

Compare this to Lesson 1: the "credential" (client_id + client_secret) never reaches the gateway at all — only the token does. That's a real security improvement, not just more machinery: a leaked API key in Lesson 1 was reusable forever until you noticed and rotated it by hand; a leaked access token here expires on its own, usually in minutes.

Why asymmetric signing matters here, concretely. Lesson 3's auth-service and the gateway both know one shared secret (HS256) — fine, because you run both. Keycloak is genuinely external: it signs with a private key only it holds and publishes only the matching public key (RS256) via JWKS. The gateway can verify a signature was made by that private key, but could never forge one. That's the asymmetric trust Lesson 3 explicitly said was being simulated — this lesson is where it becomes literally true.

Check your grip before you build

Lesson 3's gateway and auth-service both know JWT_SECRET. What's different about how the gateway trusts Keycloak?

The gateway never learns a secret at all — it fetches Keycloak's public key from JWKS and uses that only to verify signatures. It has no way to mint a valid token itself, unlike Lesson 3 where knowing the shared secret meant either side technically could.

In Lesson 1, if someone captured a request to the gateway, they got a reusable API key. What do they get if they capture a request under today's flow, and why is that better?

Just the access token — not the client_id/client_secret that minted it, since those are only ever sent to Keycloak's token endpoint, not to the gateway. And the token itself expires quickly, so a captured one is only useful for a short window.

A JWT's header carries a kid field. What problem does it solve?

An authorization server can have more than one signing key active at once (mid-rotation, for example). kid tells the verifier exactly which key in the JWKS to check the signature against, instead of trying every published key.

Step 2 — create a realm and a service-account client (admin console)

Run docker compose up keycloak, then open http://localhost:8080 and log in with the admin credentials from Step 1.

  1. Create a new realm — call it gateway-demo. (A realm is Keycloak's word for an isolated tenant: its own users, clients, and keys.)
  2. Inside it, create a new client — call it dead-letter-monitor. This represents the calling service, not a person.
  3. On the client's settings: turn Client authentication ON (this makes it a confidential client — publicClient=false — meaning it can hold a secret safely) and turn on Service accounts roles (serviceAccountsEnabled=true — this is the switch that actually enables the client-credentials grant for this client).
  4. Save, then open the client's Credentials tab and copy the generated client secret — you'll need it in Step 3.

Terms recap: confidential client and service account are in GLOSSARY.md. Source: Keycloak server admin guide — client credentials grant.

Step 3 — get a token by hand first (prove the flow before wiring code)

Before touching the gateway, get a token straight from Keycloak's token endpoint, so you can see exactly what the gateway will receive: 

curl -X POST http://localhost:8080/realms/gateway-demo/protocol/openid-connect/token \
  -d "grant_type=client_credentials" \
  -d "client_id=dead-letter-monitor" \
  -d "client_secret=<the secret from Step 2>"

Paste the access_token field into jwt.io's debugger. Compare its shape to Lesson 3's user JWT — same header.payload.signature structure, but look at the header's alg (should be RS256, not HS256) and the payload's azp/clientId claims — there's no sub representing a person, because there isn't one.

Step 4 — the gateway verifies via JWKS

New file gateway/src/auth/clientCredentialsAuth.ts. New dependencies: jwks-rsa (fetches and caches Keycloak's public keys) alongside the jsonwebtoken you already have.

Notice what's missing on purpose: no audience check yet, and no check that this specific client (not just any valid Keycloak client in the realm) is allowed to hit dead-letters. Both are one line each once you've got the basic flow working — ask me once verification succeeds and we'll tighten it.

Step 5 — wire it into the dead-letters route

In gateway/src/index.ts, on the /api/v1/dead-letters mount specifically — this route's requireRole("admin") gets replaced by clientCredentialsAuthMiddleware, not layered alongside it. Think about why before you write the line: what would req.user even mean on a request with no human behind it?

Verify it yourself: repeat the curl from Step 3 to get a fresh token, then call GET /api/v1/dead-letters through the gateway with Authorization: Bearer <that token> → should succeed. No header at all → 401. Tamper one character of the token → 401 (signature no longer matches the key Keycloak published). Wait past the token's expiry (check exp in the decoded payload — Keycloak's default is short) and retry the same token → 401 again, this time for being expired rather than forged.

Where this points next

You now have a real external authorization server in the stack, and one route trusting it without ever knowing its secret. Still open: what happens when a route needs to accept both a Keycloak client token and an auth-service user token (multi-issuer trust) — and the other half of OAuth2, authorization-code, where a human logs in through an actual browser redirect instead of a script POSTing credentials directly. Refresh tokens — letting a client get a new access token without re-authenticating from scratch — round out Phase C after that.
