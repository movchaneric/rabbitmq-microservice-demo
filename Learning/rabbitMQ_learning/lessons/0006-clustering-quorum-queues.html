Lesson 6: Clustering & Quorum Queues

Tied to mission: the single point of failure you found yourself while testing Lesson 5

Where you are

Lesson 5 proved order-service survives RabbitMQ going away and coming back. But you noticed the gap yourself: something still has to bring RabbitMQ back. Right now that's one Docker container — docker-compose.yml defines exactly one rabbitmq service. If that node's disk dies, or the host it's on disappears, there's no "back" to come back to. That's a single point of failure, and no amount of client-side reconnect logic fixes it — this is a different layer entirely.

The concept: clustering + quorum queues

A RabbitMQ cluster is multiple broker nodes that share exchanges, bindings, and (with the right queue type) queue contents — clients can connect to any node and see the same topology. On its own, clustering shares definitions across nodes, but a queue's actual messages still normally live on just one node unless you use a replicated queue type.

That's what a quorum queue is: declared with the queue argument x-queue-type: "quorum", its messages are replicated across multiple cluster nodes using the Raft consensus algorithm — by default, up to three members, one per node. As long as a majority of those members are up, the queue keeps working, even if a node is completely gone. A 3-member quorum queue tolerates 1 node failure; a 5-member one tolerates 2.

This connects directly back to Lesson 3. Publisher confirms only confirm a message once RabbitMQ has "taken responsibility" for it — with a quorum queue, that now specifically means the message has been replicated to a majority of members before the confirm fires. The two features compound: confirms without quorum queues means "one node has it"; confirms with quorum queues means "most of the cluster has it."

Primary sources: RabbitMQ Docs — Clustering Guide and RabbitMQ Docs — Quorum Queues.

Check your understanding

Q1. What shared secret must be identical across every node for them to even be allowed to talk to each other?

Expected: "erlang cookie" — set via RABBITMQ_ERLANG_COOKIE. Mismatched cookies mean nodes can't authenticate with each other at all.

Q2. What algorithm does a quorum queue use to keep its replicas in agreement?

Expected: "raft consensus" — the same family of algorithm used by etcd, Consul, and many other distributed systems for exactly this problem.

Q3. How many of a quorum queue's members need to be up for it to keep working — all of them, or what?

Expected: "a majority" — a 3-member queue tolerates 1 node down, a 5-member queue tolerates 2. Losing a majority, not just one node, is what actually breaks it.

The exercise

This one's a bigger infrastructure change than previous lessons — a new docker-compose.yml topology, not just application code. Nothing gets changed in your actual docker-compose.yml until you say go — read through this first.

1. Three-node cluster in docker-compose

Each node needs the same Erlang cookie, a resolvable hostname, and to be on a shared network so they can find each other:

services:
  rabbitmq1:
    image: rabbitmq:3-management
    hostname: rabbitmq1
    environment:
      RABBITMQ_ERLANG_COOKIE: "___"          # pick a secret string — same on all 3
    ports:
      - "5672:5672"
      - "15672:15672"
    networks: [rabbitmq-cluster]

  rabbitmq2:
    image: rabbitmq:3-management
    hostname: rabbitmq2
    environment:
      RABBITMQ_ERLANG_COOKIE: "___"          # must match rabbitmq1 exactly
    networks: [rabbitmq-cluster]
    depends_on: [rabbitmq1]

  rabbitmq3:
    image: rabbitmq:3-management
    hostname: rabbitmq3
    environment:
      RABBITMQ_ERLANG_COOKIE: "___"          # must match rabbitmq1 exactly
    networks: [rabbitmq-cluster]
    depends_on: [rabbitmq1]

networks:
  rabbitmq-cluster:
    driver: bridge

Notice only rabbitmq1 exposes ports to your host — the other two are only reachable from inside the Docker network for now. Ask me why that's fine for a cluster (hint: think about what a client actually needs to reach vs. what nodes need to reach each other).

2. Join the cluster

After docker compose up -d, nodes 2 and 3 need to explicitly join node 1:

docker exec rabbitmq2 rabbitmqctl stop_app
docker exec rabbitmq2 rabbitmqctl join_cluster rabbit@rabbitmq1
docker exec rabbitmq2 rabbitmqctl start_app

docker exec rabbitmq3 rabbitmqctl stop_app
docker exec rabbitmq3 rabbitmqctl join_cluster rabbit@rabbitmq1
docker exec rabbitmq3 rabbitmqctl start_app

Verify with:

docker exec rabbitmq1 rabbitmqctl cluster_status

All three nodes should appear in the running list.

3. Convert one queue to a quorum queue

In inventory-service/src/rabbitmq/topology.ts, add one argument to q.orders.inventory's existing assertQueue call: 

await channel.assertQueue(QUEUES.ORDERS_INVENTORY, {
  durable: true,
  arguments: {
    "___": "quorum",   // the queue-type argument
    "x-dead-letter-exchange": EXCHANGES.ORDERS_DLX,
    "x-dead-letter-routing-key": ROUTING_KEYS.ORDER_FAILED,
  },
});

This queue already exists (non-quorum) from every previous lesson — RabbitMQ will reject re-declaring it with different arguments. You'll need to delete the existing q.orders.inventory (management UI or rabbitmqctl delete_queue) before restarting inventory-service so it gets recreated as quorum. Ask me if you want to talk through why that precondition-failure happens before doing it.

Verify it works

  1. docker exec rabbitmq1 rabbitmqctl cluster_status — 3 nodes listed.
  2. Management UI (http://localhost:15672) → Queues → q.orders.inventory should show type quorum and 3 nodes under "Members."
  3. Force inventory failures on, place a couple orders so messages sit in the queue (or just place normal orders and act fast).
  4. docker stop whichever container is currently the quorum queue's leader (shown in the UI) — not rabbitmq1 if that's the one your services' RABBITMQ_URL points at, to isolate "queue survives a node loss" from "my client's connection survives a node loss" (that second one is next lesson's problem, not this one's).
  5. Confirm in the UI: the queue is still there, still has its messages, on the remaining 2 nodes — a new leader was elected automatically.
Deliberately out of scope for this lesson: your services still connect to a single hardcoded host (RABBITMQ_URL=amqp://guest:guest@localhost:5672). If that specific node goes down, your client's connection still drops — Lesson 5's reconnectForever would kick in, but it'd need somewhere else to reconnect *to*. Multi-host client connections (or a load balancer in front of the cluster) is the natural next problem this surfaces — flagging it, not solving it here.
You've demonstrated actual broker-level fault tolerance — not "the client is patient," but "the data itself survives losing a machine."
