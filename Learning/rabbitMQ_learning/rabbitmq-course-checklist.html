RabbitMQ Course Checklist

Udemy curriculum vs. what's actually been built and verified in this project

This lines up the Udemy course outline against JOURNEY.md / MISSION.md, so we can see at a glance what's covered before picking this back up later. Publish/Subscribe (fanout) is intentionally left out of this checklist for now, per your call.

RabbitMQ Patterns

4 done · 3 missing (of 7 tracked; fanout set aside)

DONE
Common Patterns (overview)
Absorbed implicitly by building and extending the demo across every lesson.
DONE
Simple Queue
The basic publish → queue → consume path underlies the whole demo (e.g. order-service → q.orders.inventory).
DONE
Work Queues / Task Queues (fair dispatch)
This is exactly what Lesson 2 (Prefetch/QoS) covered and live-tested with a 6-order burst.
MISSING
Publish/Subscribe based on Routing (direct exchange)
Never built as its own exercise — the demo went straight to a topic exchange. A direct exchange with plain routing keys (no wildcards) is a distinct, simpler pattern worth doing on its own.
DONE
Publish/Subscribe based on Topics
The baseline topology (built before this teaching workspace) already uses a topic exchange (ex.orders) with routing keys like order.placed.
MISSING
Publish/Subscribe based on Headers
A headers exchange (routing by message header match instead of routing key) has never been used anywhere in this project.
MISSING
RPC — Remote Procedure Call
No request/reply pattern (correlationId + replyTo queue) exists anywhere — every flow so far is fire-and-forget pub/sub, never "ask and wait for an answer."

Set aside for now: Publish/Subscribe (fanout) — not tracked in this checklist.

RabbitMQ Advanced Hands-On

2 done · 1 partial · 5 missing · 1 not applicable (of 9)

MISSING
Custom Exchanges — Consistent Hash Exchange
Never used; would need the community rabbitmq-consistent-hash-exchange plugin.
DONE
Dead Letter Exchange (DLX)
Already working before this workspace started, then extended in Lesson 1.
DONE
Delay Schedule / Delay Publication Model
Lesson 1's TTL parking lot is this pattern — a no-consumer queue with x-message-ttl used purely to delay delivery.
PARTIAL
Data Safety — Transactions & Publisher Confirms
Publisher Confirms is done (Lesson 3). Classic AMQP transactions (tx.select/tx.commit) were never covered — lower priority, since confirms are the modern, higher-throughput replacement for the same guarantee.
MISSING
Vhosts
Everything so far runs in the default vhost — multi-tenant isolation via separate vhosts hasn't come up.
MISSING
Policies
Settings like TTL and HA have all been set as per-queue arguments in code, not as broker-level, pattern-matched Policies (which apply to any matching queue/exchange without touching application code).
MISSING
Lazy Queues — memory optimization
Never used; all queues so far keep messages in memory (or classic mirrored/quorum replication) rather than paging to disk to save RAM on very large backlogs.
MISSING
Priority Queues
Every queue so far treats all messages equally — x-max-priority and per-message priority has never been used.
N/A
NT Service
Windows-native service registration for RabbitMQ. This project runs entirely in Docker — not applicable unless we ever install RabbitMQ natively on Windows.

Conceptual comparison only (no separate hands-on) — worth revisiting once Shovels/Federation are actually built, to make the comparison concrete instead of theoretical.
SUPERSEDED
Highly Available (Mirrored) Queues
The legacy HA mechanism, replaced by Quorum Queues (which this project already uses). Worth knowing it exists and why it was deprecated, but not worth building — quorum queues are the modern answer to the same problem.
DONE
Quorum Queues
Lesson 6 — live-verified q.orders.inventory survives killing rabbitmq1.
MISSING
Partitions
Never deliberately tested a network partition (split-brain) or configured a cluster_partition_handling mode (e.g. pause-minority). Killing a node (Lesson 6) is not the same failure mode as a partition where all nodes stay up but can't see each other.
