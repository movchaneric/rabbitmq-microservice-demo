The concept: what Redis is

Redis is an in-memory data structure store. Contrast that with something like Postgres: Postgres keeps data on disk, understands tables and SQL joins, and is built to safely hold data far bigger than RAM. Redis keeps (almost) everything in RAM, has no query language and no joins, and in exchange is extremely fast — a single lookup is a hash-table access in memory, not a disk read.

Redis is also its own separate running program (a server), not a library you import that does the work in-process. That server sits there listening on a TCP port (default 6379). Anything that wants to talk to it — redis-cli, your Node app, another language entirely — is a client: a separate program that opens a network connection to the server and sends it commands, one at a time, getting a reply back for each.

Hold onto this distinction — it's exactly what tripped up Lesson 2: "building a client object" and "connecting to the server" are two different steps. The first is just constructing a value in your program (instant, no network involved yet). The second is real network I/O — opening a TCP connection to wherever the Redis server actually lives — which takes time and can fail, so it has to be a deliberate, awaited step. Every Redis client library keeps these separate for that reason.

Data in Redis is organized as keys mapped to values, and the value at a key can be one of a handful of built-in shapes. You don't need to use all of these yet — just recognize the names, since different lessons ahead will reach for different ones:

  • String — a single value (text, or a number Redis will let you increment). What we've used so far, and what rate limiting's first algorithm (fixed window) will use as a counter.
  • Hash — a key holding multiple field→value pairs, like a small object.
  • List — an ordered sequence of values.
  • Set — an unordered collection with no duplicates.
  • Sorted Set — like a Set, but every member has a score it's ordered by. Sliding-window rate limiting (a later lesson) uses this.

One more fundamental: any key can have a TTL (time-to-live) attached. Without one, a key lives forever — Redis never deletes it on its own. With one, Redis deletes it automatically the moment the TTL hits zero, with no application code involved. That's the entire mechanism a rate limiter's "reset after N seconds" behavior is built from.

Primary source: Redis Docs — Data types and Redis Docs — Protocol spec (RESP) for what "client talks to server over a connection" actually means at the wire level (skim, don't study).

Check your understanding

Q1. Is Redis fundamentally a disk-based database like Postgres, or an ___ data structure store?

Expected: "in memory" — it keeps data in RAM, which is what makes it fast and what makes durability an explicit design question rather than a given.

Q2. Constructing a client object in your program and actually opening a network connection to the Redis server — are these the same step, or a ___ ___?

Expected: "separate step" — building the client is instant and local; connecting is real network I/O and must be awaited on its own.

Q3. If you never attach a TTL to a key, how long does it live?

Expected: "forever" — Redis only removes a key on its own if it has an expiry set. No TTL means no automatic cleanup, ever.

The exercise: redis-cli, no code

Redis should already be running from the earlier docker-compose.yml work. Get a shell talking to it — either redis-cli -h localhost -p 6379 if you have redis-cli installed locally, or docker exec -it <redis-container-name> redis-cli to run it from inside the container. Then, by hand, one at a time:

Run these and read every reply before moving to the next one

SET greeting hello
GET greeting
TYPE greeting
EXISTS greeting
EXISTS nope
DEL greeting
EXISTS greeting

SET counter 1
INCR counter
INCR counter
TTL counter

EXPIRE counter 20
TTL counter

After running the EXPIRE counter 20 block, wait past 20 seconds and run GET counter / TTL counter again yourself — watch it actually disappear rather than just trusting the docs. Ask me if any single reply surprises you; that's more useful than skimming past it.

Verify it works

  1. Every command above returned something you can explain — including why EXISTS nope returns 0 and why TTL greeting (before you set an expiry) would have returned -1.
  2. You watched counter vanish on its own once its TTL hit zero — no code ran to delete it.
You now have a working, hands-typed mental model of Redis as a server you talk to over a connection, keys mapped to typed values, and TTL-driven expiry — entirely independent of any TypeScript client library. That separation is exactly what Lesson 2 needs to land correctly this time.
