Redis Lesson 5: Token Bucket

Sliding-window smoothness without a per-request log — a bucket that refills at a steady rate instead of counting the past

Where you are

Lesson 4's sliding-window limiter fixed the boundary-burst problem, but you also read (and now know from having built it) its cost: one ZSET member per request, and a remove-add-count round trip on every single call. A client sending steadily for an hour means an ever-churning set of timestamps you have to maintain forever. Token bucket gets the same "smooth over time, not bursty at boundaries" property, but the entire state per client is just two numbers — a token count and a timestamp — regardless of how many requests that client has ever made.

The concept: a bucket that refills itself

Picture a bucket that holds at most CAPACITY tokens. It starts full. Every request costs one token. Tokens refill continuously at a fixed rate — say, one every 6 seconds — up to the cap. If the bucket has at least one token when a request arrives, the request is allowed and a token is spent; if it's empty, the request is rejected.

  • No background job refills it. Nothing runs on a timer adding tokens every few seconds. Instead, the bucket is lazily refilled: each time a request arrives, the limiter computes how much time has passed since the last time this bucket was touched, multiplies by the refill rate, and adds that many tokens (capped at CAPACITY) before deciding whether to spend one. The bucket's state is honest at the instant it's read, even though nothing updated it while it sat idle.
  • State per client: tokens and lastRefillMs. That's the whole thing. A Redis hash with those two fields replaces the ever-growing ZSET from Lesson 4.
  • Bursts are still allowed, on purpose. A client that's been idle arrives with a full bucket and can spend all CAPACITY tokens at once. What token bucket prevents is sustained overuse — once the bucket's empty, the only way to get more requests through is to wait, at exactly the refill rate. That's different from sliding window, which caps every rolling N-second slice equally with no burst allowance at all.

Why this needs a Lua script, not MULTI

Lessons 3 and 4 both used redisClient.multi() — queue up a few commands, send them as one round trip, get back an array of results. That works because none of those commands needed to look at a value before deciding what the next command should be. Token bucket can't do that: you have to read the current tokens and timestamp, compute the refill in your application logic, decide whether there's a token to spend, and only then write the new state back — and all of that has to happen as one atomic unit, or two concurrent requests could both read "1 token left," both decide to allow themselves, and both write back "0 tokens," letting two requests through on a bucket that only had room for one.

MULTI can't branch on a value it just read mid-transaction — every command in a MULTI block is queued blind before any of them run. What you need is logic that reads, computes, and conditionally writes, all atomically. Redis gives you that with EVAL: you send it a small Lua script, and Redis runs the whole script to completion, uninterrupted, before handling any other client's command. The script itself does the read, the refill math, the allow/reject decision, and the write — all inside Redis, in one round trip, with no other client's script able to interleave.

This is new, so it's given to you fully worked (per this track's rule for genuinely new mechanisms) — the Lua script below is not blanked. The blanks in this exercise are in the TypeScript around it: calling the script and reacting to its result, which by now is a pattern you've built twice.

Primary source: Redis Docs — Scripting with Lua for how EVAL guarantees atomic execution; Redis Docs — Rate limiting, "Token bucket" section, for the algorithm itself.

Expected: "atomic" (or "atomically") — the whole read-compute-decide-write sequence runs as one uninterruptible unit inside Redis. No other command, from any client, can run in the middle of it.

Q3. Lessons 3 and 4 got away with ___() instead of a Lua script because none of their commands needed to branch on a value read earlier in the same transaction — an INCR or a ZADD doesn't care what the count was before it ran.

Expected: "multi" — redisClient.multi() queues commands blind and sends them as one round trip, but nothing in the block can look at another command's result and change course. Token bucket's "read tokens, compute refill, conditionally spend one" can't be expressed that way.

Function signature: redisClient.eval()

Before the exercise blanks it out, here's exactly what this function expects and returns:

  • script (1st argument) — the raw Lua source as a string. That's TOKEN_BUCKET_SCRIPT below.
  • options.keys — a string[]. Each entry becomes KEYS[1], KEYS[2], … inside the Lua script. Only actual Redis key names go here. This script touches exactly one key (the bucket's hash), so this array has exactly one element.
  • options.arguments — a string[]. Each entry becomes ARGV[1], ARGV[2], … inside Lua. Everything else the script needs that isn't itself a Redis key goes here — capacity, refill rate, the current timestamp. node-redis requires these to actually be strings, so numbers get wrapped in String(...) before being passed.
  • Return value — whatever the Lua script's return statement produces, translated through Redis's wire protocol into a JS value. This script's last line, return { allowed, tostring(tokens) }, is a Lua table, which comes back as a JS array: [allowed, tokensString]. Lua integers arrive as JS numbers; Lua strings stay strings. TypeScript has no way to infer that shape automatically — that's why the call site below casts the result with as [number, string].

The exercise

One new file. The Lua script is given in full; the TypeScript around it has blanks where you're repeating a pattern from Lessons 3-4.

1. gateway/src/redis/tokenBucketRateLimiter.ts (new file)

import { Request, Response, NextFunction } from 'express';
import { redisClient } from './client';

const CAPACITY = ___;           // max tokens the bucket can hold (= max burst size)
const REFILL_PER_SECOND = ___;  // tokens added per second, e.g. 1/6 for one every 6s

// Given in full: reads tokens+timestamp, applies refill, decides allow/reject, writes
// back — all atomically, in one round trip.
const TOKEN_BUCKET_SCRIPT = `
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refillPerSecond = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(bucket[1])
local lastRefillMs = tonumber(bucket[2])

if tokens == nil then
  tokens = capacity
  lastRefillMs = now
end

local elapsedSeconds = (now - lastRefillMs) / 1000
tokens = math.min(capacity, tokens + elapsedSeconds * refillPerSecond)

local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end

redis.call('HSET', key, 'tokens', tostring(tokens), 'ts', tostring(now))
redis.call('EXPIRE', key, 3600)

return { allowed, tostring(tokens) }
`;

export async function tokenBucketRateLimiter(req: Request, res: Response, next: NextFunction) {
  const key = `rate-limit:orders:bucket:${___}`;  // same client identifier as Lessons 3-4
  const now = Date.now();

  const [allowed, tokensRemaining] = await redisClient.eval(TOKEN_BUCKET_SCRIPT, {
    keys: [___],
    arguments: [String(CAPACITY), String(REFILL_PER_SECOND), String(___)],
  }) as [number, string];

  if (!allowed) {
    const tokensNow = Number(tokensRemaining);
    const secondsUntilOneToken = (1 - tokensNow) / ___;
    const retryAfterSeconds = Math.ceil(secondsUntilOneToken);
    res.set('Retry-After', String(retryAfterSeconds));
    return res.status(___).json({
      error: 'Too Many Requests',
      retryAfterSeconds,
    });
  }

  ___;  // within limit — let the request continue to the proxy
}

Notes on the blanks:

  • keys: [___] is the same key you just built above — it's passed separately from arguments because Redis Cluster uses the declared KEYS to know which node a script's data lives on. You won't hit that in this single-node setup, but the two-array shape (keys vs. arguments) is how EVAL always works, cluster or not.
  • The third argument is what the script calls now inside Lua — it needs the same JS timestamp you already computed for const now.
  • secondsUntilOneToken's divisor is the same refill-rate constant used inside the Lua script — how long until enough tokens accumulate for exactly one more request.

Verify it works

  1. Restart gateway.
  2. Send CAPACITY requests to POST http://localhost:3000/api/v1/orders back-to-back. All should succeed — that's the burst allowance. The next one should 429 with a Retry-After header.
  3. Wait roughly 1 / REFILL_PER_SECOND seconds and send one more request. It should succeed — confirm you're not waiting for a full window reset the way Lesson 3's fixed window would have forced you to, just for one token's worth of time.
  4. Inspect the hash directly: redis-cli HGETALL "rate-limit:orders:bucket:<your-ip>" (from Lesson 1) and confirm tokens and ts are the only two fields, and that tokens moves toward CAPACITY the longer you wait between requests.
