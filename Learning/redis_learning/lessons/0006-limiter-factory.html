Redis Lesson 6: Generalizing the Rate Limiter

Turning one hardcoded middleware into a factory that can serve any route

Where you are

All three limiters you've built so far — rateLimiter.ts, slidingWindowRateLimiter.ts, tokenBucketRateLimiter.ts — build their Redis key the same hardcoded way: 

const key = `rate-limit:orders:bucket:${req.ip}`;

The route name (orders) and the tuning constants (CAPACITY, REFILL_PER_SECOND) are baked directly into the module — there's exactly one middleware, hardwired to exactly one route, with exactly one configuration. The moment inventory-service or notification-service needs its own rate limit — probably with different numbers, since inventory writes and notification sends aren't the same kind of traffic as order placement — today's shape means copy-pasting the entire file and hand-editing the copy. That's the "will we have to duplicate this three more times?" problem you flagged while looking at slidingWindowRateLimiter.ts.

The concept: a factory function

The fix is a pattern you've almost certainly used before in a different shape: a function that returns a configured function, instead of a function that is the configured behavior. Right now, tokenBucketRateLimiter is a middleware. After this lesson, createTokenBucketLimiter(config) is a function that builds a middleware — a different one each time you call it, each remembering its own scope, capacity, and refillPerSecond.

  • Closures do the remembering. When createTokenBucketLimiter({ scope: "orders", capacity: 5, refillPerSecond: 1/6 }) runs, it returns an inner async function (req, res, next). That inner function references scope, capacity, and refillPerSecond from its enclosing scope — it doesn't need them passed in again on every request, because a closure keeps a live reference to the variables that were in scope when it was created. Call the factory twice with different config, and you get two independent middlewares, each closed over its own values.
  • The Lua script doesn't change at all. TOKEN_BUCKET_SCRIPT has no route-specific logic in it — it just operates on whatever key and numbers it's given. Only the TypeScript wrapper around it needed to become configurable.
  • scope replaces the hardcoded "orders" in the key — that one parameter is what actually solves the duplication problem. Everything else (capacity, refillPerSecond) was already a "magic number" you'd want to tune per route anyway; making it a parameter instead of a module constant is the same fix applied consistently.
Nothing about the algorithm changes. This lesson is a pure refactor — same Lua script, same atomicity guarantee, same refill math. The only thing moving is where the configuration lives: from module-level constants (shared, fixed at import time) to factory parameters (one set per call, chosen at mount time).

Check your understanding

Q1. The mechanism that lets the returned middleware "remember" its own capacity and refillPerSecond without those being passed in on every request is called a ___.

Expected: "closure" — the inner function keeps a live reference to the variables in scope where it was defined, even after createTokenBucketLimiter has returned and those variables would otherwise be out of reach.

Q2. Of the three values a config object needs (scope, capacity, refillPerSecond), the one that's actually responsible for fixing the "duplicate the whole file per route" problem — as opposed to just being a tunable number — is ___.

Expected: "scope" — capacity and refillPerSecond were always going to want per-route values eventually, but it's scope replacing the hardcoded route name in the Redis key that means the same file can now serve any route without its keys colliding with another route's keys.

Q3. True or false: after this refactor, TOKEN_BUCKET_SCRIPT (the Lua source itself) needs to change to support multiple routes.

Expected: "no" — the script only ever sees KEYS[1] and some numbers in ARGV. It has no idea what route it's being used for, and never needed to. Only the TypeScript that constructs the key and passes the config in needed to become parameterized.

The exercise

Refactor tokenBucketRateLimiter.ts from "a middleware" into "a function that builds a middleware." Blanks are where the shape actually changes; everything else (the Lua script, the refill math) is copied over unchanged from what you already wrote.

1. gateway/src/redis/tokenBucketRateLimiter.ts (refactor)

import { Request, Response, NextFunction } from "express";
import { redisClient } from "./client";

// Unchanged — copy this over exactly as you have it now.
const TOKEN_BUCKET_SCRIPT = `
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refillPerSecond = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(bucket[1])
local lastRefillMs = tonumber(bucket[2])

if tokens == nil then
  tokens = capacity
  lastRefillMs = now
end

local elapsedSeconds = (now - lastRefillMs) / 1000
tokens = math.min(capacity, tokens + elapsedSeconds * refillPerSecond)

local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end

redis.call('HSET', key, 'tokens', tostring(tokens), 'ts', tostring(now))
redis.call('EXPIRE', key, 3600)

return { allowed, tostring(tokens) }
`;

interface TokenBucketConfig {
  scope: string;           // becomes the route segment in the Redis key, e.g. "orders"
  capacity: number;        // max tokens the bucket can hold
  refillPerSecond: number; // tokens added per second
}

export function createTokenBucketLimiter(config: TokenBucketConfig) {
  const { ___, ___, ___ } = config;  // pull all three out of config once, up front

  return async function tokenBucketRateLimiter(req: Request, res: Response, next: NextFunction) {
    const key = `rate-limit:${___}:bucket:${req.ip}`;  // scope replaces the old hardcoded "orders"
    const now = Date.now();

    const [allowed, tokensRemaining] = (await redisClient.eval(TOKEN_BUCKET_SCRIPT, {
      keys: [key],
      arguments: [String(___), String(___), String(now)],  // capacity, refillPerSecond — from the closure now, not module constants
    })) as [number, string];

    if (!allowed) {
      const tokensNow = Number(tokensRemaining);
      const secondsUntilOneToken = (1 - tokensNow) / ___;  // refillPerSecond, same as before
      const retryAfterSeconds = Math.ceil(secondsUntilOneToken);
      res.set("Retry-After", String(retryAfterSeconds));
      return res.status(429).json({
        error: "Too Many Requests",
        retryAfterSeconds,
      });
    }

    next();
  };
}

2. gateway/src/index.ts (mount via the factory)

import { createTokenBucketLimiter } from "./redis/tokenBucketRateLimiter";

app.use("/api/v1/orders", createTokenBucketLimiter({
  scope: ___,
  capacity: ___,
  refillPerSecond: ___,
}));

Use the same numbers you already had (5 and 1/6) — this step should change how the limiter is configured, not what it actually enforces.

Verify it works

  1. Restart gateway. Confirm /api/v1/orders still behaves identically to before the refactor — same burst size, same refill timing, same 429 shape. If the numbers you pass in match what you had, nothing about the observable behavior should change.
  2. Check the Redis key directly with redis-cli — it should still be rate-limit:orders:bucket:<your-ip>, just now produced from scope instead of a hardcoded string.
  3. The actual point of this lesson: prove the duplication problem is solved, not just refactored away in theory. Mount a second, independent limiter on a different route with different numbers: 
    app.use("/api/v1/inventory", createTokenBucketLimiter({
  scope: "inventory",
  capacity: 20,
  refillPerSecond: 2,
}));
    Confirm both routes rate-limit independently (hitting one doesn't affect the other's bucket) using two different Redis keys — with zero new files and zero copy-pasted logic.
One implementation now serves any number of routes, each with its own limit, its own Redis keys, and no shared state between them — without duplicating a single line of the actual rate-limiting logic. The open design question flagged during Lesson 4 is closed.

Optional follow-up

The same transformation applies just as well to rateLimiter.ts (Lesson 3) and slidingWindowRateLimiter.ts (Lesson 4) — same idea, module constants and the hardcoded "orders" segment become factory parameters. Not required to move on, but worth doing on your own once, purely as repetition: the second and third time you apply a pattern is where it actually sticks.
