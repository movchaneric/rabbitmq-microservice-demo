Redis Lesson 7: Cache-Aside for Inventory Stock

New phase, new service — Redis as a read cache instead of a rate-limit ledger

Where you are

Lessons 1–6 closed out the rate-limiting arc: gateway now guards two routes with a reusable token-bucket factory. Per MISSION.md's "next phase," this lesson starts a different problem in a different service — inventory-service gets a Redis-backed cache in front of GET /inventory. Two design decisions are already made, so this lesson builds toward a specific target instead of surveying options:

  • What's cached: the stock-level read (getStock() in inventory-service/src/data.ts) — the highest-read, lowest-write data this service has.
  • Invalidation strategy: TTL-only. No code on the write path changes at all; the cache entry just expires on its own after a short window and the next read repopulates it. The tradeoff you're accepting: for up to that TTL, a read can return slightly stale stock numbers. That's fine here because nothing in this codebase currently decrements stock on order placement anyway (check ordersInventoryConsumer.ts — it simulates success/failure but never touches the stock object), so there's no correctness case to worry about yet, only the mechanism.

The concept: cache-aside

Cache-aside (a.k.a. "lazy loading") is the pattern where your application code, not Redis, is responsible for keeping the cache populated. The shape is always the same four steps, run in order on every read:

  1. Check the cache for the key.
  2. Hit: return the cached value. Done — the real data source is never touched.
  3. Miss: read the real value from the source of truth (here, getStock()).
  4. Write that value into the cache (with a TTL) before returning it, so the next read is a hit.

This is different from write-through, where the cache gets updated immediately as part of every write, so it's never stale but every write path has to know about the cache. Cache-aside pushes all of that complexity onto the read path instead and leaves writes completely alone — which is exactly why it's the right fit for a TTL-only strategy: the cache is allowed to be behind reality for a bounded window, so nothing needs to reach into the write path to keep it correct.

Redis only stores strings (for this data type). getStock() returns a JS object, but a Redis string value has to be, well, a string. That means the write side needs JSON.stringify before SET, and the read side needs JSON.parse after GET — a serialization step that fixed window/sliding window/token bucket never needed, because those only ever stored plain numbers as strings.

New Redis client calls this lesson uses

Both of these are node-redis methods you haven't called directly yet (previous lessons used multi()/incr/ttl, zAdd/zRangeWithScores, and eval — this is the first plain key-value read/write).

  • redisClient.get(key: string): Promise<string | null> — fetches the string value stored at key. Returns null (not an error, not an empty string) if the key doesn't exist — that's exactly the "cache miss" signal the cache-aside logic branches on.
  • redisClient.set(key: string, value: string, options?: { EX?: number }): Promise<string | null> — stores value (must already be a string) at key. The { EX: seconds } option sets a TTL atomically as part of the same command — no separate EXPIRE call needed, and no gap between the two the way there would be with SET then EXPIRE as two round trips. Resolves to "OK" on success.

Check your understanding

Q1. When redisClient.get(key) is called on a key that doesn't exist, what does it resolve to?

Expected: "null" — not an error, not undefined, not an empty string. That's the signal cache-aside code checks to decide hit vs. miss.

Q2. getStock() returns a JS object. What has to happen to it before it can be passed as the value argument to redisClient.set()?

Expected: "JSON.stringify" — Redis string values are strings; the object has to be serialized on the way in and parsed back with JSON.parse on the way out.

Q3. With TTL-only invalidation, which side of the data flow needs zero new code — the read path, or the ___ ___?

Expected: "write path" — that's the whole appeal of TTL-only: staleness is bounded by time alone, so nothing that writes stock data needs to know the cache exists.

The exercise

0. Setup

inventory-service has never talked to Redis before, so a couple of things need to exist first — run these yourself:

  • npm install redis inside inventory-service/.
  • Add REDIS_URL=redis://localhost:6379 to both inventory-service/.env and inventory-service/.env.example (same value gateway already uses — same Redis instance, both docker-compose services can share it).

1. inventory-service/src/redis/client.ts (new file)

Full code — this is the exact same construct-vs-connect wiring from Lesson 2, just a new service importing it. Nothing new to reason about here, so no blanks. 

import { createClient } from "redis";

if (!process.env.REDIS_URL) {
  throw new Error("REDIS_URL is not set");
}

export const redisClient = createClient({ url: process.env.REDIS_URL })
  .on("error", (err) => console.error("[redis] client error:", err))
  .on("ready", () => console.log("[redis] connected and ready"))
  .on("reconnecting", () => console.warn("[redis] reconnecting..."))
  .on("end", () => console.warn("[redis] connection closed"));

export async function connectRedis(): Promise<void> {
  await redisClient.connect();
}

export async function disconnectRedis(): Promise<void> {
  await redisClient.close();
}

2. inventory-service/src/redis/stockCache.ts (new file)

This is where the actual cache-aside logic lives — the shape that's new this lesson. Blanks are the get/set calls and the serialization boundary from the sections above. 

import { redisClient } from "./client";
import { getStock } from "../data";
import { Stock } from "../types";

const CACHE_KEY = "cache:inventory:stock";
const CACHE_TTL_SECONDS = 10;

export async function getCachedStock(): Promise<Stock> {
  const cached = await redisClient.___(CACHE_KEY);

  if (cached) {
    console.log("[cache] hit");
    return JSON.___(cached) as Stock;
  }

  console.log("[cache] miss");
  const stock = getStock();
  await redisClient.___(CACHE_KEY, JSON.___(stock), { ___: CACHE_TTL_SECONDS });

  return stock;
}

3. inventory-service/src/index.ts (edit)

Wire the connection at startup and swap the route handler to go through the cache. Full code for the parts that changed — this is mechanical once stockCache.ts exists. 

import 'dotenv/config';
import express, { Request, Response } from 'express';
import { connect } from './rabbitmq';
import { connectRedis } from './redis/client';
import { getCachedStock } from './redis/stockCache';
import { toggleForceFailure } from './data';
import { log } from './logger';

const app = express();
app.use(express.json());

app.get('/inventory', async (_req: Request, res: Response) => {
  res.json(await getCachedStock());
});

app.post('/inventory/toggle-fail', (_req: Request, res: Response) => {
  const current = toggleForceFailure();
  log(`Force failure toggled → ${current ? 'ON (100% fail)' : 'OFF'}`);
  res.json({ forceFailure: current });
});

async function start(): Promise<void> {
  await connect();
  await connectRedis();
  app.listen(process.env.PORT, () => {
    log(`Listening on port ${process.env.PORT}`);
  });
}

start().catch(err => {
  console.error('[inventory-service] Fatal:', (err as Error).message);
  process.exit(1);
});

Note that getStock is no longer imported directly in index.ts — the route only knows about getCachedStock() now. getStock is still imported, just one layer down, inside stockCache.ts.

Verify it works

  1. docker compose up -d redis (if it isn't already running), then start inventory-service.
  2. Hit GET http://localhost:3002/inventory once. Terminal should log [cache] miss.
  3. Hit it again immediately — this time [cache] hit, and the JSON response should be identical.
  4. Check it directly: redis-cli GET cache:inventory:stock should show the JSON-stringified stock object, and TTL cache:inventory:stock should show a number counting down from 10.
  5. Wait past 10 seconds without hitting the route, then request again — back to [cache] miss, proving the key actually expired rather than living forever.
inventory-service now has a working cache-aside read path: same source of truth, same response shape, but repeated reads within the TTL window never touch getStock() again. The "next phase" MISSION.md flagged after the rate-limiting arc has a first real implementation.
