CI/CD Lesson 2: Docker Multi-Stage Build

Tied to mission: give order-service a real, runnable container image

Where you are

order-service now has a real test and a real CI gate (Lesson 1) — verified live, including two genuine failures you debugged yourself. But CI only proves the code works when run with ts-node straight from source. Nothing about this repo can be deployed anywhere yet, because nothing has ever been packaged into something a hosting platform (or anyone else's machine) can just run. That's what an image is for.

The concept: why two `FROM` lines, not one

A container image is a snapshot: a filesystem plus a default command to run. You could write a single-stage Dockerfile that installs everything — typescript, ts-node, every dev dependency — and runs the app straight from .ts source, same as your local npm start. It would work. It would also ship a full TypeScript toolchain inside something whose only job, in production, is running already-compiled JavaScript — bigger, slower to pull, and carrying build tools the running app has no use for.

A multi-stage build fixes this: an earlier stage (the builder stage) has the full toolchain and compiles TypeScript to plain JavaScript. The final stage (the runtime stage) starts from a fresh base image and copies over only the compiled output (COPY --from=builder) — none of the builder stage's layers carry over automatically. What ships is exactly: Node itself, production dependencies, and compiled JS. Nothing else.

This is the same shape as Lesson 1's builder/runtime split in your CI job — there, `npm ci` installed everything (dev + prod) because tests need `vitest`. Here, the final image explicitly does not want dev dependencies at all. Same underlying idea (don't carry more than the next step needs), applied to a different boundary.

Primary source — read this before the exercise: Docker Docs — Multi-stage builds. Full annotated example: this workspace's own cheat sheet.

Check your understanding

Three short-answer questions, one word each.

Q1. What Dockerfile instruction starts a brand-new stage, with its own fresh base image?

Expected: "FROM" — each `FROM` line starts over from a base image; nothing from a previous stage is present unless you explicitly `COPY --from=` it in.

Q2. Check order-service/tsconfig.json yourself — what's the compiled JavaScript output folder called (its `outDir`)?

Expected: "dist" — this is exactly the folder the runtime stage needs to `COPY --from=builder`, and nothing else from the builder stage.

Q3. Why does the reference sheet's Dockerfile `COPY package*.json ./` and `RUN npm ci` before `COPY . .` (the rest of the source), instead of copying everything at once?

Expected: "cache" (Docker layer caching) — if only source files change on a rebuild, and the dependency-install layer's inputs (`package*.json`) didn't change, Docker reuses that layer instead of re-running `npm ci` from scratch every time.

FROM node:20-alpine

Verify it works

  1. Build it: docker build -t order-service:local ./order-service
  2. Check the size: docker images order-service:local — note the number, you'll want it for comparison once you containerize a service without multi-stage later, if you ever do.
  3. Bring up the existing broker/cache: docker-compose up -d (from the repo root, unchanged from your RabbitMQ/Redis tracks).
  4. Find the network Compose actually created: docker network ls — look for one containing rabbitmq-cluster.
  5. Run your image on that network, pointing at the containers by their service names instead of localhost: 
    docker run --rm -p 3001:3001 \
  --network <the-network-name-you-just-found> \
  -e PORT=3001 \
  -e RABBITMQ_URL=amqp://guest:guest@haproxy:5672 \
  -e REDIS_URL=redis://redis:6379 \
  order-service:local
  6. From another terminal: curl -X POST http://localhost:3001/orders -H "Content-Type: application/json" -d '{"productId":"sku-1","quantity":2,"customerEmail":"a@b.com"}' — you should get a 201 with the order back.
  7. curl http://localhost:3001/orders should show it in the list.

If the container can't reach RabbitMQ/Redis at all (connection refused, not just slow), the most likely cause is the --network flag pointing at the wrong network name, or a typo in haproxy/redis as hostnames — Docker's embedded DNS only resolves other containers' service names if they're on the exact same user-defined network.
