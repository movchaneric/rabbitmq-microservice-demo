CI/CD Lesson 3: Pushing to GitHub Container Registry

Tied to mission: get order-service's image somewhere a hosting platform can actually reach

Where you are

order-service has a real CI gate (Lesson 1) and a real multi-stage image that builds and runs correctly (Lesson 2) — but that image only exists on your laptop. This lesson makes CI build that same image and push it to GitHub Container Registry (ghcr.io), tagged by the exact git commit that produced it — not latest. Once this lands, the image is somewhere real: reachable by anything with the right credentials, including Render in the next lesson.

The concept: registries, and why not `latest`

A registry stores built images by name and tag, the same way npm's registry stores packages by name and version. docker push sends an image there; docker pull retrieves it — which is exactly what a hosting platform does under the hood when it deploys your image, without ever touching your source code or running a Docker build itself.

Why GHCR specifically: since this repo already lives on GitHub, a workflow can authenticate to ghcr.io using the GITHUB_TOKEN GitHub automatically issues to every run — no separate account, no extra credentials to create and store as a secret.

Why tag by git SHA instead of `latest`: latest is a label that gets silently overwritten on every push. Deploy `latest` today, and if it's broken, there's no way to look at a running container and know which commit actually produced it, and no clean way to roll back to a specific earlier version by name. Tagging by the commit SHA (order-service:7f38a79...) makes every pushed image permanently traceable back to the exact code that built it.

This job only runs on a real push to `main`, not on every PR. Building and pushing an image for every single PR commit would mean cluttering the registry with images that may never actually deploy — same CI-vs-CD boundary from Lesson 1 (the `pull_request` event tests a change; only a `push` to `main` should ever produce something that might get deployed).

Primary source — read this before the exercise: GitHub Docs — Publishing Docker images.

Check your understanding

Three short-answer questions, one word each.

Q1. On `docker/build-push-action`, what boolean input actually tells it to publish the image to the registry, instead of just building it locally inside the runner and discarding it?

Expected: "push" — `push: true`. Without it, the action still builds the image (useful for a PR job that just wants to confirm the Dockerfile works), but never sends it anywhere.

Q2. The workflow already has access to `secrets.GITHUB_TOKEN` — but that alone isn't enough to push a package. What job-level YAML key also has to explicitly grant write access?

Expected: "permissions" — `permissions: packages: write`. `GITHUB_TOKEN`'s default scope doesn't assume every job wants to publish packages; you opt in per-job.

Q3. What's the property of a git-SHA-based tag (as opposed to `latest`) that makes it trustworthy for tracing exactly what code is running in production?

Expected: "immutable" — a given SHA tag can only ever refer to the image built from that exact commit. `latest` is a floating pointer that gets reassigned; a SHA tag never does.

The exercise

One file, extended — add a second job to the same workflow from Lesson 1 (.github/workflows/order-service-ci.yaml), right alongside the existing test job. Blanks (___) are yours to fill.

.github/workflows/order-service-ci.yaml — add this job

  push-image:
    needs: ___                       # which job must succeed first — no point pushing an image for broken code
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: ___                  # what access does actually pushing a package need?

    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ___              # which registry are we authenticating to?
          username: ${{ github.actor }}
          password: ${{ secrets.___ }}   # which built-in secret authenticates this, no setup required?

      - uses: docker/build-push-action@v6
        with:
          context: ___                # which folder has order-service's own Dockerfile?
          push: ___                   # from Q1 — what actually publishes it?
          tags: ghcr.io/${{ github.repository_owner }}/order-service:${{ ___ }}   # tag by what, not "latest"?

Note this job has no `defaults.run.working-directory` like the `test` job does — that key only affects `run:` steps (plain shell commands). Every step here is `uses:` (a packaged action), so instead the folder is passed explicitly as the `context` input on the one step that needs it. The last blank is a built-in GitHub Actions context value (not a secret) that holds the full SHA of the commit that triggered this run — check the github context reference if you're not sure of its exact name.

Verify it works

  1. Push this change to main directly (it's a workflow file change, not `order-service/**`, so note: this won't trigger the path filter — you'll need to also touch something under order-service/** in the same push, or temporarily widen the path filter, to actually see `push-image` run. Ask me if this catches you out.)
  2. Watch the Actions tab: you should see two jobs this time — test, then push-image starting only after it turns green.
  3. On GitHub, go to your repository's main page → right sidebar → Packages. You should see a new order-service package, with a tag matching the exact commit SHA from your push.
  4. Push again with a trivial change (a comment) and confirm a second, distinct SHA-tagged image appears — proving each push produces its own permanently traceable image, nothing overwritten.
order-service's image now lives somewhere real — versioned, traceable to an exact commit, and reachable by anything with the right credentials. Nothing about deploying it depends on your laptop anymore.
