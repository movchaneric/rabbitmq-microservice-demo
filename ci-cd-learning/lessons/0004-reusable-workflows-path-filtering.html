CI/CD Lesson 4: Reusable Workflows & Per-Job Path Filtering

Tied to mission: stop copy-pasting order-service-ci.yaml four more times

Where you are

order-service has a complete pipeline: test, then build-and-push to GHCR, tagged by commit SHA. Four more services need the exact same shape of pipeline. Your own instinct, stated directly before this lesson, was right: just widening paths: to list all 5 services in one workflow file doesn't work, because GitHub's built-in on.push.paths gates the whole workflow, not individual jobs inside it — a change to gateway/ would still run order-service's test and push jobs too. This lesson fixes that properly, with the two pieces named in the mission: reusable workflows (write the test→build→push logic once) and per-job path filtering (only run it for the service that actually changed).

The concept: a dispatcher, a reusable workflow, and a filter between them

dorny/paths-filter is an action that, inside one workflow run, inspects exactly which files changed and produces a true/false output per named group you define — e.g. "did anything under order-service/ change? Did anything under gateway/ change?" Each answer is available to every other job in that same run, which is the piece GitHub's built-in paths: key can't do at all.

Reusable workflows solve the copy-paste problem separately: a workflow file with on: workflow_call instead of on: push isn't triggered directly — it's called, job-to-job, by another workflow, and can take inputs (parameters). Your entire test + push-image pattern becomes one such file, parameterized by which service it's running for.

Put together, one dispatcher workflow does three things: (1) run paths-filter once to find out what changed, (2) for each service, a small job gated by if: on that service's filter output, that (3) — only if it runs at all — calls the one reusable workflow, passing in which service this is. 

on: push / pull_request
  |
  v
job "changes" -- dorny/paths-filter --> order-service: true, gateway: false, ...
  |                                              |
  v (if order-service == 'true')                 v (if gateway == 'true' -- skipped this run)
job "order-service"                       job "gateway"
  uses: ./service-ci.yml                     uses: ./service-ci.yml
  with: { service: order-service }           with: { service: gateway }

Primary sources — read these before the exercise: dorny/paths-filter (README has the exact filter syntax), GitHub Docs — Reusing workflows.

Check your understanding

Three short-answer questions, one word each.

Q1. What YAML key, written directly on a job (not a step), tells that job to call an entire separate workflow file instead of running its own steps?

Expected: "uses" — the same keyword steps use to call an action (`uses: actions/checkout@v4`), reused at the job level for a different purpose: calling a whole reusable workflow (`uses: ./.github/workflows/service-ci.yml`).

Q2. In a reusable workflow's `on: workflow_call:` block, what key declares the parameters a caller is required (or allowed) to pass in?

Expected: "inputs" — each one gets a `type` and whether it's `required`. Inside the reusable workflow, you read one back with `${{ inputs.name }}`.

Q3. A caller job's `if:` checks a filter output against which string value, to confirm that service's directory actually changed in this push/PR?

Expected: "true" (as a string: `== 'true'`) — `paths-filter`'s outputs are strings, not real booleans, so the comparison is against the literal text `'true'`, not YAML's `true` keyword.

The exercise

Two new files, plus deleting one old one. This lesson wires up only `order-service` through the new setup, end to end — proving the mechanism works with the one service that already has everything (tests, Dockerfile). Porting the same Dockerfile/test/build pattern to the other 4 services is deliberately saved for right after this, once you're confident this shape actually works.

1. .github/workflows/service-ci.yml (new file — the reusable workflow)

This is your existing `order-service-ci.yaml` logic, parameterized. Blanks:

name: Reusable service CI

on:
  workflow_call:
    inputs:
      service:
        required: ___        # must the caller always supply this?
        type: ___             # what kind of value is a service name?

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ${{ ___ }}   # read the input back — which service's folder?
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
      - run: npm ci
      - run: npm test

  push-image:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: ./${{ ___ }}                                            # same input, again
          push: true
          tags: ghcr.io/${{ github.repository_owner }}/${{ ___ }}:${{ github.sha }}   # and again, in the tag

2. .github/workflows/ci.yml (new file — the dispatcher)

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      order-service: ${{ steps.filter.outputs.order-service }}
      gateway: ${{ steps.filter.outputs.gateway }}
      inventory-service: ${{ steps.filter.outputs.inventory-service }}
      notification-service: ${{ steps.filter.outputs.notification-service }}
      dead-letter-service: ${{ steps.filter.outputs.dead-letter-service }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            order-service:
              - 'order-service/**'
            gateway:
              - 'gateway/**'
            inventory-service:
              - 'inventory-service/**'
            notification-service:
              - 'notification-service/**'
            dead-letter-service:
              - 'dead-letter-service/**'

  order-service:
    needs: ___                                              # which job produces the filter outputs?
    if: needs.___.outputs.___ == '___'                       # job name, filter name, and the value from Q3
    uses: ./.github/workflows/service-ci.yml
    with:
      service: order-service

Notice `changes`' `outputs:` block already lists all 5 services, and the `filters:` block already checks all 5 paths — even though only `order-service` has a caller job so far. That's intentional: the detection step doesn't care yet which services have a pipeline; it just reports what changed. Ask me if it's unclear why these are already fully filled in for all 5 while the caller job below is only for one.

3. Delete .github/workflows/order-service-ci.yaml

It's now fully replaced by `ci.yml` + `service-ci.yml` together — leaving both would mean `order-service` runs its test/push pipeline twice on every push.

Verify it works

  1. Push a real change under order-service/**. In the Actions tab, you should see the new run named after ci.yml's jobs: changes first, then order-service (which internally runs `test` then `push-image` — check its logs, they're the reusable workflow's jobs, just nested under this call).
  2. Open the changes job's logs and find the `dorny/paths-filter` step's output — confirm `order-service: true` and every other service `false`.
  3. Push a change under a different service (e.g. `gateway/`) and confirm: the `changes` job still runs (it always does), but no `order-service` job appears in this run at all — its `if:` evaluated false.
  4. Confirm the registry still gets a new SHA-tagged order-service image on the `order-service/**` push, same as Lesson 3.
One reusable workflow, parameterized by service name, plus one dispatcher that only calls it for services that actually changed. Adding the remaining 4 services from here is copying a 6-line caller block, not a 25-line workflow file.
