Lesson 1: Delayed Retry with a TTL Parking Lot

Tied to mission: close the "instant retry" gap in dead-letter-service

Where you are

dead-letter-service already reads the x-death header and republishes a failed order back to ex.orders up to MAX_RETRIES times before giving up — that's a real bounded-retry mechanism, and you built it yourself (commit 10ebec9). The gap: every retry republishes instantly. If inventory-service is failing because it's overloaded, retrying with zero delay just adds to the pile.

The pattern: parking lot

Instead of your consumer code republishing immediately, you hand the message to a queue with no consumer — a "parking lot" — that has a x-message-ttl. Nothing reads from it. The message just sits until its TTL expires, at which point RabbitMQ itself (not your code) dead-letters it onward to the real queue via that parking-lot queue's own x-dead-letter-exchange. 

q.orders.inventory --nack--> ex.orders.dlx --> q.orders.dlx (your consumer)
                                                      |
                                        publish to ex.orders.retry
                                                      v
                                            q.orders.retry  (TTL, no consumer)
                                                      |
                                              TTL expires
                                                      v
                                    ex.orders / order.placed --> q.orders.inventory again

Primary source — read this before coding: CloudAMQP — Delayed messages with RabbitMQ (the "TTL and Dead Letter Exchanges" section specifically). Also see RabbitMQ Docs — Dead Letter Exchanges for the authoritative argument names.

Check your understanding

Three short-answer questions. Type an answer, hit Check, then compare.

Q1. What queue-level setting makes a message wait before anything happens to it?

Expected: "message ttl" — set via the x-message-ttl queue argument (milliseconds). It applies to the queue, not an individual publish call.

Q2. What's the broker mechanism that moves an expired message out of the parking-lot queue, without your application code running?

Expected: "dead lettering" — the same DLX mechanism you already use for failures also fires on TTL expiry. That's what lets the parking lot have zero consumer code.

Q3. Your existing deadLetterConsumer already reads a header to decide when to stop retrying and record a permanent failure instead. What does that header track?

Expected: "retry count" (the workspace glossary calls this the x-death header's count field — see GLOSSARY.md). This doesn't change in this lesson — the parking lot sits between retries, it doesn't replace the counter.

The exercise

2. dead-letter-service/src/rabbitmq/topology.ts

Add the parking-lot exchange and queue. This queue is never consumed from — it only needs the TTL and dead-letter arguments:

await channel.assertExchange(EXCHANGES.ORDERS_RETRY, EXCHANGE_TYPES.___, { durable: true });

await channel.assertQueue(QUEUES.ORDERS_RETRY, {
  durable: true,
  arguments: {
    'x-message-ttl': ___,                        // milliseconds — pick a delay you can watch happen
    'x-dead-letter-exchange': ___,                // where should it land once TTL expires?
    'x-dead-letter-routing-key': ___,             // what routing key gets it back into q.orders.inventory?
  },
});

await channel.bindQueue(QUEUES.ORDERS_RETRY, EXCHANGES.ORDERS_RETRY, ROUTING_KEYS.ORDER_RETRY);

Stuck on which exchange/routing key sends it back to q.orders.inventory? Re-read inventory-service/src/rabbitmq/topology.ts — the answer is already declared there. Ask me if it's still not clicking.

3. dead-letter-service/src/rabbitmq/consumers/deadLetterConsumer.ts

Find the retry branch — currently:

channel.publish(EXCHANGES.ORDERS, ROUTING_KEYS.ORDER_PLACED, payload, {
  persistent: true,
  headers: msg.properties.headers,
});

Change the target so it goes to the parking lot instead of straight back to the live exchange (keep the headers forwarding — you still need x-death to keep incrementing):

channel.publish(EXCHANGES.___, ROUTING_KEYS.___, payload, {
  persistent: true,
  headers: msg.properties.headers,
});

Update the log line too — it currently says "RETRYING → republished", which is no longer accurate the instant it happens.

Verify it works

  1. docker-compose up -d && npm start
  2. Force a failure: POST /api/v1/inventory/toggle-fail, then POST /api/v1/orders
  3. Open http://localhost:15672 → Queues. You should see the message sitting in your new parking-lot queue with a non-zero message count, then draining to zero once the TTL you picked elapses.
  4. Watch dead-letter-service logs — you should see the order arrive back in q.orders.inventory only after the delay, not instantly.
  5. Turn failure mode back off (toggle-fail again) before the retry lands, and confirm it succeeds on that attempt instead of exhausting MAX_RETRIES.
You now have retry-with-backoff using nothing but queue arguments — no scheduler, no extra library, no polling loop. The broker is doing the waiting for you.
