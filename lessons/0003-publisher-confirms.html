Lesson 3: Publisher Confirms

Tied to mission: close the last named gap — the publish side of reliability

Where you are

Everything you've built so far — parking-lot retry, prefetch — is about what happens after a message is safely inside RabbitMQ. Nothing yet covers the very first step: order-service's publish itself. 

channel?.publish("ex.orders", "order.placed", payload, { persistent: true });
res.status(201).json(order);

That publish() call returns a boolean synchronously — but that boolean only tells you whether amqplib's local write buffer is full (its own kind of backpressure signal), not whether RabbitMQ actually received, routed, and persisted the message. The very next line replies 201 Created to the customer regardless. If the connection drops in the split second between "we called publish" and "the broker actually wrote it to disk," the order is gone — and the customer already has a success response telling them otherwise.

The concept: acks, but for the publisher

You already know the consumer side of this: no message is ever really "gone" until your code calls ack. Publisher confirms are the same idea, flipped — RabbitMQ acks you, the publisher, once it's actually taken responsibility for the message.

To use them in amqplib, you create the channel differently: 

const channel = await connection.createConfirmChannel();  // instead of createChannel()

Then every publish() on that channel accepts a callback that fires once RabbitMQ confirms (or rejects) that specific message: 

channel.publish(exchange, key, payload, options, (err) => {
  if (err) {
    // RabbitMQ nacked it, or the channel died before confirming
  } else {
    // truly safe — RabbitMQ has it
  }
});

Primary source — read the "Strategy #1, #2, #3" section before coding: RabbitMQ Tutorial 7 — Reliable Publishing with Publisher Confirms. Also see RabbitMQ Docs — Consumer Acknowledgements and Publisher Confirms.

Three strategies, one tradeoff (throughput vs. simplicity):
  • Sync per-message — publish, wait for that one confirm, then publish the next. Simplest, slowest (one network round-trip per message).
  • Batch — publish many, then wait once for the whole batch. Much faster, but a failure tells you "something in this batch failed," not which one.
  • Async (what you'll build) — publish and register a callback per message; keep publishing without blocking. Best throughput, and you still get a precise per-message result.

Check your understanding

Q1. What does a publisher confirm actually tell the publisher, once received?

Expected: "taken responsibility" — RabbitMQ is asserting it has the message (routed and, for a durable queue + persistent message, on disk), not just that it accepted your TCP write.

Q2. What has to change about *how the channel itself is created* to enable confirms at all?

Expected: "channel creation" — createConfirmChannel() instead of createChannel(). Confirms aren't a flag you set later; they're a different kind of channel from the start.

Q3. In the async strategy you're about to build, how granular is the result you get back — per batch, or per what?

Expected: "per message" — that's the whole advantage of async over batch: full throughput, but you still know exactly which message succeeded or failed.

The exercise

Two files in order-service. Fill it in yourself using the pattern above.

1. order-service/src/rabbitmq/connection.ts

Find the line that creates the channel:

channel = await connection.createChannel();

Change it to a confirm channel:

channel = await connection.___();

2. order-service/src/index.ts

Currently:

channel?.publish("ex.orders", "order.placed", payload, { persistent: true });
res.status(201).json(order);

Move the response so it only fires inside the confirm callback — success only after RabbitMQ actually confirms, an error response if it doesn't: 

channel?.publish("ex.orders", "order.placed", payload, { persistent: true }, (err) => {
  if (err) {
    log(`PUBLISH FAILED → orderId=${order.orderId}`);
    res.status(___).json({ error: "___" });
  } else {
    res.status(___).json(order);
  }
});

What status code fits an "we accepted your request but couldn't actually queue it" failure? Think about what's semantically true here — ask me if you want a second opinion before picking one.

Verify it works

  1. Add a timestamp log right before the publish call and another inside the callback — confirm there's a real (if small) gap between them. That gap is the round-trip to RabbitMQ and back; with the old code, the response went out before that gap even started.
  2. docker-compose up -d && npm start, then POST /api/v1/orders as usual — should still return 201, just a few milliseconds later than before.
  3. Stretch (optional, not required to finish the lesson): stop the RabbitMQ container (docker-compose stop rabbitmq) and try posting an order — watch what error surfaces now versus what the old fire-and-forget code would have silently swallowed.
The customer's "order placed" response is now only ever true. Before this, a success response was a guess; now it's a guarantee backed by RabbitMQ itself.
