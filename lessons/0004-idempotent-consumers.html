Lesson 4: Idempotent Consumers

Tied to mission: fix the notification double-send bug you found yourself

Where you are

Back in Lesson 1 you traced the full order lifecycle and noticed something: q.orders.notification is bound to ex.orders/order.placed — the exact same key q.orders.retry dead-letters back into on every retry. That means every single retry cycle re-sends a "your order is confirmed" email, even though the order hasn't actually succeeded yet (and might still fail permanently). You flagged it and moved on. This lesson is coming back to fix it.

The concept: at-least-once, not exactly-once

RabbitMQ — like essentially every message broker — guarantees at-least-once delivery, never exactly-once. Duplicates aren't a bug or an edge case; they're a normal, expected consequence of how reliability works at all. Two concrete sources of duplication exist in this repo already:

  • The parking-lot retry (your own design) — re-publishes to order.placed, which every bound queue receives again, not just the one that actually failed.
  • The universal one — if a consumer crashes after processing a message but before calling ack, RabbitMQ redelivers it. Nothing about your code can prevent this; it's inherent to manual ack.

The fix is never "stop the duplicates from arriving" — you can't, and shouldn't try. The fix is making the consumer's effect the same whether it processes a message once or five times. That's the idempotent consumer pattern.

Primary source: microservices.io — Idempotent Consumer pattern (Chris Richardson's pattern catalog — the standard reference for this). Also see RabbitMQ Docs — Reliability Guide for where duplication fits into the broader reliability picture.

The general recipe: give every message a stable identifier (you already have one — orderId), and before your consumer produces any externally-visible effect (sending an email, charging a card, writing a row), check whether that identifier has been handled before. If yes, skip the effect — but still ack the message; a duplicate isn't a failure, it's just a no-op.

The exercise

Two files in notification-service. Fill it in yourself.

1. notification-service/src/data.ts

Currently just an array and two functions. Add a way to track which orderIds have already been notified:

import { Notification } from './types';

const notifications: Notification[] = [];
const notifiedOrderIds = new ___<string>();  // what structure gives O(1) "have I seen this before"?

export function addNotification(notification: Notification): void {
  notifications.push(notification);
  notifiedOrderIds.___(notification.orderId);  // record it
}

export function getNotifications(): Notification[] {
  return notifications;
}

export function hasNotified(orderId: string): boolean {
  return notifiedOrderIds.___(orderId);  // check it
}

2. notification-service/src/rabbitmq/consumers/orderNotificationConsumer.ts

Before building and sending the notification, check whether this order was already handled. If so, log it and ack anyway — a duplicate isn't a failure: 

const order: Order = JSON.parse(msg.content.toString());

if (___(order.orderId)) {
  console.log(`DUPLICATE → skipping already-notified orderId=${order.orderId}`);
  channel.ack(msg);
  return;
}

const notification: Notification = { ... };  // unchanged

Verify it works

  1. docker-compose up -d && npm start
  2. POST /api/v1/inventory/toggle-fail → force failures ON
  3. POST /api/v1/orders — this one will retry via the parking lot every 8 seconds.
  4. Watch notification-service's logs: the first delivery should send normally, but every subsequent delivery of the same order.placed event (from each retry cycle) should now log DUPLICATE → skipping instead of sending another email.
  5. GET /api/v1/notifications — confirm only one entry exists for that orderId, no matter how many times inventory retried.
notification-service now behaves correctly under RabbitMQ's real delivery guarantee, instead of accidentally relying on "it'll probably only arrive once."
