Lesson 5: Connection & Channel Recovery

Tied to mission: the gap we stumbled into ourselves while testing Lesson 3

Where you are

Remember the confusing stretch during Lesson 3, where stopping RabbitMQ and starting it back up left order-service completely dead until you manually restarted npm start? That wasn't a fluke. Look at connection.ts: createConnection(retries = 5) only ever runs once, at boot, inside connect(). If the connection dies after that point — broker restart, network blip, anything — nothing in this codebase notices. The module just keeps holding a reference to a dead channel forever, until a human restarts the process.

The concept: connections die, and something has to notice

amqplib's connection object is an EventEmitter. It emits 'close' whenever the connection ends — whether from a clean shutdown or a failure — and 'error' when something goes wrong on the wire. Recovery means: listen for those events, and when they fire, run the entire connect sequence again (new connection, new channel, re-assert topology) rather than leaving the old, dead reference sitting in place.

A sharp, easy-to-miss gotcha: in Node, an EventEmitter that emits an 'error' event with no listener attached throws and crashes the process. So even before you write any reconnect logic, just attaching something to connection.on('error', ...) is a real, separate safety fix — right now, a raw connection error would take the whole service down harder than it needs to.

Primary source: amqp-node/amqplib GitHub Issue #153 — "How to reestablish connection after a failure?" (straight from the library's own maintainers/community). Practical walkthrough: Ecostack — RabbitMQ Auto Reconnect in Node.js.

Worth knowing it exists, even though you're hand-rolling it here to actually learn the mechanism: amqp-connection-manager — a wrapper that does exactly this reconnect-and-resetup pattern for you in real production code.

Check your understanding

Q1. What event does amqplib's connection object emit whenever the connection ends, clean or not?

Expected: "close event" — fires on clean shutdown too, not just failures, so it's the one reconnect logic should key off of.

Q2. In Node, what happens if an EventEmitter emits 'error' with no listener attached?

Expected: "crashes process" — an unhandled 'error' event throws. This is exactly why attaching even a no-op-ish handler matters independent of reconnect logic.

Q3. On reconnect, how much of the original startup logic should re-run — just the connection, or the what?

Expected: "entire sequence" — new connection, new channel, and re-asserting topology (safe, since assertExchange/assertQueue are idempotent) — not just a bare reconnect with stale setup.

The exercise

Scoped to order-service only for now — same pattern would apply to the other three services as a natural follow-up, not required here.

1. order-service/src/rabbitmq/connection.ts

Track the raw connection object too, not just the channel, so it can be reached from outside this module. amqp.connect() resolves to a type called ChannelModel — check node_modules/@types/amqplib/index.d.ts if you want to confirm that yourself. 

import amqp, { ConfirmChannel, ___ } from "amqplib";
import { log } from "../logger";

let channel: ConfirmChannel | null = null;
let connection: ___ | null = null;

export async function createConnection(retries = 5): Promise<ConfirmChannel> {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      connection = await amqp.connect(process.env.RABBITMQ_URL as string);
      channel = await connection.createConfirmChannel();
      log("Connected to RabbitMQ");
      return channel;
    } catch (err) {
      // ...unchanged retry/backoff logic below
    }
  }
  throw new Error("Failed to connect to RabbitMQ");
}

export function getChannel(): ConfirmChannel | null {
  return channel;
}

export function ___(): ___ | null {
  return connection;
}

2. order-service/src/rabbitmq/index.ts

After the initial connect + topology setup succeeds, attach listeners on the connection. On 'close', re-run connect() itself — the same function this code is already inside of: 

export async function connect(): Promise<void> {
  const channel = await createConnection();
  await setupTopology(channel);
  log('RabbitMQ ready');

  ___()?.on('close', () => {
    log('RabbitMQ connection closed — reconnecting...');
    connect().catch((err) => log(`Reconnect failed: ${(err as Error).message}`));
  });
  ___()?.on('error', (err) => {
    log(`RabbitMQ connection error: ${(err as Error).message}`);
  });
}

Don't forget to import whatever you named the new getter from connection.ts. Ask me if you're unsure why the 'error' listener doesn't also need to call connect() — think about what 'close' already guarantees happens right after an error.

Verify it works

  1. docker-compose up -d && npm start, confirm the happy path works (POST /orders → 201).
  2. docker compose stop rabbitmq — do not touch npm start this time. Watch order-service's logs: you should see "RabbitMQ connection closed — reconnecting..." followed by several "Connect attempt X/5 failed" lines.
  3. docker compose start rabbitmq — within a few seconds (depending on which retry attempt is in flight when it comes back), you should see "Connected to RabbitMQ" / "RabbitMQ ready" again, with no manual restart of npm start.
  4. POST /orders again — should be back to 201, fully self-healed.
Known limitation, worth naming rather than hiding: if RabbitMQ stays down longer than all 5 retry attempts take to exhaust (~30s of backoff), this particular reconnect gives up permanently until the process is restarted — it doesn't retry forever. Production systems often reconnect indefinitely instead. Out of scope for this exercise, but worth knowing before calling this "done."
order-service now survives a RabbitMQ restart without a human touching it — the exact scenario that confused us both a few lessons ago.
