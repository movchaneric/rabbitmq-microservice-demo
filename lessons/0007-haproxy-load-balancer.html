Lesson 7: HAProxy in Front of the Cluster

Tied to mission: the gap you found yourself — 2 healthy nodes, but nothing routes to them

Where you are

Lesson 6 proved q.orders.inventory's data survives losing rabbitmq1 — a new leader gets elected among the survivors automatically. But you immediately hit the real gap yourself: with rabbitmq1 down, you couldn't reach the management UI or publish a single order, even though two perfectly healthy nodes were sitting right there. Nothing was pointing clients at them.

The concept: a stable address in front of an unstable topology

The fix is a load balancer sitting in front of all three nodes. Clients stop connecting to any individual RabbitMQ node entirely — they connect to the load balancer's one stable address, and it decides, based on active health checks, which node actually receives that connection. If a node goes down, the load balancer simply stops routing to it; clients never need to know a topology change happened at all.

HAProxy is the standard tool for this in front of RabbitMQ — it handles raw TCP proxying (what AMQP needs) as well as HTTP (for the management UI), with configurable active health checks per backend server.

Critical rule, easy to get wrong: HAProxy must not run on one of the RabbitMQ cluster nodes. If it did, losing that machine would take down both a RabbitMQ node and your only entry point at the same time — reintroducing the exact single point of failure this lesson is trying to remove.

Primary source: Yannick Pereira-Reis — "RabbitMQ high available cluster with docker and HAProxy" (widely-referenced, with a companion GitHub repo).

Check your understanding

Q1. After this change, how many distinct RabbitMQ hostnames should your Node services' code need to know about?

Expected: "one stable" — the load balancer's address. This is a pure infrastructure fix; zero application code changes.

Q2. Where should HAProxy itself run — on one of the cluster nodes, or where?

Expected: "not cluster" (i.e. not on a cluster node) — otherwise losing that node takes the load balancer down with it.

Q3. What does HAProxy use to decide whether to keep routing traffic to a given node?

Expected: "active health" (health checks) — HAProxy actively probes each backend on an interval, rather than waiting to fail a real request first.

The exercise

Since you're keeping rabbitmq1 down deliberately, this gets built and verified against a 2-of-3 cluster from the start — a good, honest test.

1. New file: haproxy.cfg (repo root)

global
    log stdout format raw local0

defaults
    log global
    mode tcp
    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend amqp_front
    bind *:5672
    default_backend amqp_back

backend amqp_back
    balance roundrobin
    server rabbitmq1 rabbitmq1:5672 check inter 2000 rise 2 fall 3
    server rabbitmq2 rabbitmq2:5672 check inter 2000 rise 2 fall 3
    server rabbitmq3 rabbitmq3:5672 check inter 2000 rise 2 fall 3

frontend mgmt_front
    bind *:15672
    default_backend mgmt_back

backend mgmt_back
    balance roundrobin
    server rabbitmq1 rabbitmq1:15672 check inter 2000 rise 2 fall 3
    server rabbitmq2 rabbitmq2:15672 check inter 2000 rise 2 fall 3
    server rabbitmq3 rabbitmq3:15672 check inter 2000 rise 2 fall 3

listen stats
    bind *:8404
    mode http
    stats enable
    stats uri /
    stats refresh 5s

That check inter 2000 rise 2 fall 3 means: probe every 2 seconds, need 2 consecutive successes to mark a server back up, 3 consecutive failures to mark it down. Ask me why "3 failures before marking down" is safer than "1 failure" if this isn't obvious.

2. docker-compose.yml — two changes

Remove the ports: block from rabbitmq1 entirely — it should no longer be reachable directly from your host, only through HAProxy now. Then add a new haproxy service: 

haproxy:
  image: haproxy:2.9
  volumes:
    - ./haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro
  ports:
    - "5672:5672"
    - "15672:15672"
    - "8404:8404"
  networks: [rabbitmq-cluster]
  depends_on: [rabbitmq1, rabbitmq2, rabbitmq3]

Notice RABBITMQ_URL in every service's .env stays exactly amqp://guest:guest@localhost:5672 — unchanged. That's the whole point: localhost:5672 now reaches HAProxy instead of rabbitmq1 directly, and your application code never needs to know the difference.

Verify it works

  1. docker compose up -d haproxy (and anything else not already running)
  2. Open http://localhost:8404 — HAProxy's stats page. You should see rabbitmq1 marked down (red) for both backends, and rabbitmq2/rabbitmq3 marked up (green) — live proof it's actively health-checking, not just blindly round-robining.
  3. http://localhost:15672 should now load the management UI again — routed by HAProxy to whichever node is healthy, with rabbitmq1 still down.
  4. Restart order-service (nothing else needs to change) and confirm POST /api/v1/orders returns 201 again — through the load balancer, with zero code changes, while rabbitmq1 stays off.
  5. Stretch: bring rabbitmq1 back up and watch it turn green in the stats page on its own, with no restart of HAProxy needed.
Losing a node no longer means losing access to the system at all — the load balancer absorbed exactly the failure mode you discovered by hand in Lesson 6.
