Lesson 2: Prefetch / QoS

Tied to mission: give inventory-service backpressure control over its own queue

Where you are

Every consumer you've written so far (ordersInventoryConsumer, orderNotificationConsumer, deadLetterConsumer) calls channel.consume(...) with no limit on how many messages RabbitMQ hands it at once. That default is unlimited — the broker will push every currently-ready message straight into that consumer's channel the moment it's connected, regardless of whether the consumer has finished processing (acked) anything yet.

The concept: prefetch as backpressure

channel.prefetch(n) (AMQP's basic.qos) tells RabbitMQ: "never let more than n unacknowledged messages sit with this consumer at once." Until an ack (or nack) frees up a slot, the broker holds the rest back in the queue instead of pushing them.

  • prefetch(1) — strict one-at-a-time. Maximum fairness (if you later run multiple consumer instances on the same queue, work spreads by actual speed, not a static round-robin), but no pipelining — throughput drops.
  • prefetch(100–300) — the range the RabbitMQ team and CloudAMQP both point to as a solid default for most workloads: enough in flight to keep throughput up, bounded enough to avoid one consumer hoarding the entire queue.
  • no prefetch set (current state of this repo) — a burst of messages gets dumped entirely onto whichever consumer is currently connected, with zero regard for how fast it's actually working through them.

Primary source: RabbitMQ Docs — Consumer Prefetch. Practical numbers: CloudAMQP — How to Optimize the RabbitMQ Prefetch Count.

Check your understanding

Q1. What does RabbitMQ's management UI call the number of messages delivered to a consumer but not yet acked or nacked?

Expected: "unacked count" — visible per-queue in the management UI. This is exactly the number prefetch puts a ceiling on.

Q2. With no prefetch limit set, if 20 messages are ready and one consumer is connected, how many will the broker push to it immediately?

Expected: "all of them" — unlimited prefetch means unlimited push. This is the exact behavior you're about to make visible in the exercise below.

Q3. What method call, made once per channel, sets this limit in amqplib?

Expected: "channel prefetch" — channel.prefetch(n), typically called right after the channel is created, before consuming starts.

The exercise

Goal: make the "no backpressure" problem visible first, then fix it — in inventory-service only. No full solution below, same as last time — fill it in using what you just read.

1. inventory-service/src/rabbitmq/consumers/ordersInventoryConsumer.ts

Add an artificial processing delay so a burst of orders doesn't all finish instantly — otherwise you won't be able to see anything in the UI before it's over. Make the consume callback async and await a delay before the existing ack/nack logic: 

channel.consume(QUEUES.ORDERS_INVENTORY, async (msg) => {
  if (!msg) return;
  const order: Order = JSON.parse(msg.content.toString());

  await new Promise((resolve) => setTimeout(resolve, ___));  // pick a delay you can watch

  // ...existing shouldFail() / ack / nack logic below, unchanged
});

2. Observe the problem before fixing it

Don't add prefetch yet. Restart the stack, then fire off a burst — e.g. run POST /api/v1/orders 10 times in a couple seconds (a quick shell loop is fine). Open http://localhost:15672 → Queues → q.orders.inventory and watch the Ready vs Unacked columns while your delay is still running. What do you expect Unacked to jump to, given no limit is set?

3. inventory-service/src/rabbitmq/index.ts

Now fix it. Add the prefetch call in connect(), on the channel, before startConsumer(channel) runs: 

const channel = await createConnection();
await channel.prefetch(___);   // what value, and why that one over 1 or 300?

Re-run the same burst test. Unacked should now be capped at whatever number you chose, with the rest sitting in Ready until a slot frees up.

Verify it works

  1. Run the burst before adding prefetch — record what Unacked peaks at.
  2. Add channel.prefetch(n), restart, run the same burst again — confirm Unacked never exceeds n.
  3. Try n = 1 once just to feel the throughput cost — time how long the full burst takes to drain compared to your chosen production-ish value.
You can now make a RabbitMQ consumer apply real backpressure — and you've seen the difference in the management UI, not just read about it.
