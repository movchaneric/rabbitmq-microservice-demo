DLX & Retry Patterns

Quick reference — RabbitMQ dead-lettering recipes

Why a message gets dead-lettered

A queue forwards a message to its configured DLX (x-dead-letter-exchange) when any of these happen:

  • Consumer nacks or rejects it with requeue: false
  • Its TTL expires (x-message-ttl on the queue, or per-message)
  • The queue hits a length limit (x-max-length) and evicts the oldest message

Source: RabbitMQ Docs — Dead Letter Exchanges

Recipe: instant retry (what this repo had first)

original queue --nack--> DLX --> dlx queue --consumer republishes--> original exchange

Simple, but the republish happens with zero delay. If the downstream failure was "service is overloaded," this retries into the overload immediately — a thundering herd.

Recipe: parking lot (TTL-delayed retry, no plugin needed)

original queue --nack--> DLX --> parking-lot queue (has its own TTL + DLX)
                                        |
                                   TTL expires
                                        v
                              back to original exchange --> original queue

The parking-lot queue has no consumer. Messages just sit there until their TTL runs out, then the broker itself dead-letters them onward — no application code runs during the wait.

Source: CloudAMQP — Delayed messages with RabbitMQ

Gotcha: per-queue TTL (x-message-ttl) expires messages in FIFO order at the head of the queue. If message A (TTL 30s) is enqueued before message B (TTL 5s), B will not expire early — RabbitMQ only checks the head. Fine for a single fixed delay per queue; if you need multiple distinct delays, use one parking-lot queue per delay tier.

Recipe: exponential backoff

Chain multiple parking-lot queues with increasing TTLs (e.g. 5s → 30s → 5m), each dead-lettering into the next tier on expiry, with the final tier dead-lettering back to the live queue. The x-death count tells you which tier to route into.
