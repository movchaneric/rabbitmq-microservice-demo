Where you are

This is a new track, separate from the RabbitMQ lessons — see MISSION.md. The end goal is a Redis-backed rate limiter in front of order-service, but this first lesson isn't about rate limiting at all. It's about getting a Redis client talking to a real Redis instance from inside gateway, and getting comfortable with the handful of commands rate limiting actually runs on: INCR, EXPIRE, TTL, and running two of those atomically together.

The concept: why these specific commands

A rate limiter's core question is "how many requests has this client made recently, and when does that count reset?" Two Redis primitives answer that:

  • INCR key — atomically increment an integer stored at key, creating it at 0 first if it doesn't exist yet, and returning the new value. This is your request counter.
  • EXPIRE key seconds — attach a TTL to an existing key. Once it elapses, Redis deletes the key on its own — nothing in your application has to run a cleanup job. This is what makes the counter "reset" without you writing a scheduler.
  • TTL key — ask Redis how many seconds are left before a key expires (or -1 if it has no expiry, -2 if it doesn't exist). Useful for telling a client "retry after N seconds."
The bug this lesson exists to head off: calling INCR then EXPIRE as two separate round-trips has a real race — if your process crashes (or is just slow) between the two calls, that key never gets a TTL and becomes a permanent counter that never resets. Redis's MULTI/EXEC lets you queue both commands and send them as one atomic unit, so either both happen or neither does.

Primary source: Redis Docs — Node.js client (node-redis), specifically the "Connect" and "Transactions" sections. Also see Redis Docs — EXPIRE for what happens to a key's TTL under `INCR`, `SET`, etc.

Check your understanding

Q1. If you call INCR on a key that doesn't exist yet, what happens — does it error, or does something else?

Expected: "creates it" — Redis treats a missing key as 0 and INCR both creates and increments it in one atomic step, returning 1.

Q2. You INCR a key but never call EXPIRE on it. What happens to that key over time?

Expected: "never expires" — without an explicit TTL, the key lives forever (until you delete it or the server restarts without persistence). This is exactly the bug a rate limiter can't afford.

Q3. What Redis mechanism lets you run INCR and EXPIRE together as one atomic unit, so a crash between them can't happen?

Expected: "multi exec" (MULTI/EXEC, exposed in node-redis as client.multi()...exec()) — queues commands and sends them as one atomic batch.

The exercise

Four small changes across the repo. No full solution below — fill the ___ blanks yourself using the docs linked above.

1. docker-compose.yml

Add a Redis service alongside the existing RabbitMQ ones. It only needs to be reachable on the default Redis port from other containers on the same network — decide whether it needs a host port mapping too (do you want to poke at it with redis-cli from your own machine?).

redis:

  ports:
    - "___:___"              # host:container — only if you want host access
  networks: [___]            # does this need to be the same network as rabbitmq-cluster,
                              # or a new one? gateway isn't in docker-compose at all yet —
                              # it runs via `npm start` on your host. What does that mean
                              # for which network/hostname gateway should use to reach this?

That last question is the actual design decision in this exercise — think about it before just copying the RabbitMQ pattern. Ask me if you want to talk it through.

2. gateway/.env.example and gateway/.env

Add a connection string the client can use directly:

REDIS_URL=redis://___:___

3. gateway/package.json

Add the official redis package (v4/v5, promise-based — not the older callback-style API, and not ioredis) as a dependency. Run the install yourself once it's added.

4. gateway/src/redis/client.ts (new file)

Create and connect a client once at startup, so every route can import and reuse the same connection instead of reconnecting per-request:

import { createClient } from 'redis';

export const redisClient = createClient({ url: process.env.___ })
  .on('error', (err) => console.error('___', err));

export async function connectRedis() {
  await redisClient.___();
}

Then in gateway/src/index.ts, call connectRedis() before (or alongside) app.listen(...) — a route that hits Redis before the client has connected will hang or throw.

5. gateway/src/index.ts — a throwaway verification route

Not the real rate limiter (that's Lesson 2) — just enough to prove the plumbing works. Add a route that atomically increments a fixed demo key with a short TTL and reports both the new count and the remaining TTL:

app.get('/api/v1/_debug/redis-demo', async (req, res) => {
  const [count] = await redisClient.multi()
    .___('demo:hits')                 // increment
    .___('demo:hits', ___)            // set a TTL in seconds, only meaningful the
                                       // first time the key is created — think about
                                       // why re-setting it every request might be wrong
    .exec();

  const ttl = await redisClient.___('demo:hits');
  res.json({ count, ttlSecondsRemaining: ttl });
});

The comment about "only meaningful the first time" is a real design question rate limiting will need in Lesson 2 — worth sitting with now rather than just making the demo route work. Ask me about it if you want to reason it through together.

Verify it works

  1. Start Redis (however docker-compose.yml ends up structured), then npm start for the rest of the stack.
  2. Hit GET http://localhost:3000/api/v1/_debug/redis-demo repeatedly (curl or browser). count should climb 1, 2, 3... and ttlSecondsRemaining should count down.
  3. Stop hitting it and wait past the TTL, then hit it again — count should drop back to 1, proving the key actually expired rather than just resetting some in-memory variable.
  4. Optional: if you gave Redis a host port mapping, connect with redis-cli and run GET demo:hits / TTL demo:hits yourself mid-test to see the raw state your route is reading.
You now have a real Redis connection from inside this stack, and you've watched INCR/EXPIRE/TTL behave exactly as the docs describe — not just read about them. That's the entire foundation the next lesson's fixed-window rate limiter is built from.
