Redis Lesson 2: Client Wiring in the Gateway

Same destination as before, now with the client-vs-connection split from Lesson 1 in hand

Where you are

docker-compose.yml already runs Redis, and gateway/.env already has REDIS_URL. What's left is getting a Node/TypeScript client talking to it from inside gateway — the exact thing Lesson 1's redis-cli exercise was building intuition for.

The concept: one client value, shared, connected once

Remember Lesson 1's distinction: building a client is not the same step as connecting it. In the redis npm package (node-redis), that maps directly onto two separate calls:

  • createClient({ url }) — synchronous. Builds a client value with all its methods (get, set, multi, ...) already on it. No network call happens yet.
  • .connect() — asynchronous. Actually opens the TCP connection. Must be awaited, and can fail (wrong URL, server not up yet, etc.).
Why redisClient must be a value, not a function: every route in gateway needs to reuse the same open connection — that's the whole point of connecting once at startup instead of per-request. If redisClient were a function, calling it would either reconnect every time (slow, wasteful) or (as happened last time) build-and-discard a client that nothing ever holds onto. Export the client itself — the return value of createClient(...) — as a constant, and call .connect() on that same constant once, separately, at startup.

Primary source: Redis Docs — Node.js client (node-redis), "Connect" section — the exact createClient().on('error', ...).connect() shape this exercise follows.

Check your understanding

Q1. Which call builds the client value with no network I/O yet — createClient or connect?

Expected: "createClient" — synchronous, just constructs the object.

Q2. Which call actually opens the TCP connection and must be awaited?

Expected: "connect" — real network I/O, can fail, so it's async.

Q3. Should gateway/src/redis/client.ts export the client as a function that builds one on demand, or as ___ ___ every route shares?

Expected: "a value" — one shared client instance, connected once at startup.

The exercise

gateway/package.json and gateway/.env are already done (the redis package is installed, REDIS_URL is set). Full code below, not blanks — copy it in, then read the notes under each block for the "why" behind every line, since that's the part actually worth keeping.

1. gateway/src/redis/client.ts (full replacement)

import { createClient } from 'redis';

if (!process.env.REDIS_URL) {
  throw new Error('REDIS_URL is not set');
}

export const redisClient = createClient({
  url: process.env.REDIS_URL,
})
  .on('error', (err) => console.error('[redis] client error:', err))
  .on('ready', () => console.log('[redis] connected and ready'))
  .on('reconnecting', () => console.warn('[redis] reconnecting...'))
  .on('end', () => console.warn('[redis] connection closed'));

export async function connectRedis(): Promise<void> {
  await redisClient.connect();
}

export async function disconnectRedis(): Promise<void> {
  await redisClient.close();
}

Why each piece is there, not just what it does:

  • Guard clause runs before createClient, not inside it — fail fast at module load if config is missing, instead of getting a confusing connection error later.
  • redisClient is a plain exported constant — the value is the client (per Lesson 1/2's concept section), so every route that imports it shares the one real connection instead of each building its own.
  • Four event listeners, not just error — error is non-negotiable (an EventEmitter with no error listener crashes the whole Node process on the first one). ready/reconnecting/end aren't required, but without them a dropped connection is invisible until something else starts failing — cheap insurance.
  • connectRedis and disconnectRedis are separate exported functions, not run automatically at import time — connecting is a side effect with a specific right moment to happen (app startup) and a specific right moment to reverse (app shutdown); a module shouldn't decide that for you just by being imported.
  • .close(), not .quit() or .disconnect() — those are deprecated/renamed in current node-redis. .close() waits for in-flight commands to finish before closing the socket, which is what you want on a clean shutdown.

2. gateway/src/index.ts (full replacement)

import 'dotenv/config';
import express from 'express';
import { createProxyMiddleware } from 'http-proxy-middleware';
import { redisClient, connectRedis, disconnectRedis } from './redis/client';

const app = express();

app.use(createProxyMiddleware({
  target: process.env.ORDER_SERVICE_URL,
  changeOrigin: true,
  pathFilter: '/api/v1/orders',
  pathRewrite: { '^/api/v1': '' },
}));

app.use(createProxyMiddleware({
  target: process.env.INVENTORY_SERVICE_URL,
  changeOrigin: true,
  pathFilter: '/api/v1/inventory',
  pathRewrite: { '^/api/v1': '' },
}));

app.use(createProxyMiddleware({
  target: process.env.NOTIFICATION_SERVICE_URL,
  changeOrigin: true,
  pathFilter: '/api/v1/notifications',
  pathRewrite: { '^/api/v1': '' },
}));

app.use(createProxyMiddleware({
  target: process.env.DEAD_LETTER_SERVICE_URL,
  changeOrigin: true,
  pathFilter: '/api/v1/dead-letters',
  pathRewrite: { '^/api/v1': '' },
}));

app.get('/api/v1/_debug/redis-demo', async (req, res) => {
  // SET ... NX only creates the key (with its TTL) if it doesn't exist yet —
  // on every later hit this is a no-op, so the TTL is only ever set once.
  // INCR then always runs. Both queued in one MULTI/EXEC so there's no gap
  // between them a crash could land in.
  const [, count] = await redisClient.multi()
    .set('demo:hits', '0', { EX: 30, NX: true })
    .incr('demo:hits')
    .exec();

  const ttl = await redisClient.ttl('demo:hits');
  res.json({ count, ttlSecondsRemaining: ttl });
});

async function start() {
  await connectRedis();

  app.listen(process.env.PORT, () => {
    console.log(`[gateway] Listening on port ${process.env.PORT}`);
  });
}

start();

async function shutdown() {
  await disconnectRedis();
  process.exit(0);
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);

Why each piece is there, not just what it does:

  • start() awaits connectRedis() before app.listen(...) — fail fast. If Redis is unreachable, the gateway never starts accepting traffic in a half-working state; you find out immediately instead of on the first request that touches Redis.
  • SET ... NX + INCR, not INCR + EXPIRE — this is the fix for the exact gap Lesson 1 flagged: EXPIRE run unconditionally every request would keep pushing the TTL forward forever under continuous traffic, so the counter would never actually reset. NX ("only if the key doesn't already exist") makes the TTL-setting a one-time event, which is the correct fixed-window behavior.
  • SIGTERM/SIGINT handlers — without these, killing the process (Ctrl-C, or Docker/orchestrator stopping the container) drops the Redis connection mid-command instead of closing it cleanly.

Verify it works

  1. docker compose up -d redis, then npm start.
  2. Hit GET http://localhost:3000/api/v1/_debug/redis-demo repeatedly (curl or browser). count should climb 1, 2, 3... and ttlSecondsRemaining should count down.
  3. Stop hitting it and wait past the TTL, then hit it again — count should drop back to 1, proving the key actually expired rather than just resetting some in-memory variable.
  4. Optional: connect with redis-cli (from Lesson 1) and run GET demo:hits / TTL demo:hits yourself mid-test to see the raw state your route is reading.
You now have a real, shared Redis connection from inside gateway, built on a correct mental model this time — not just a fix that happened to compile. That's the entire foundation the next lesson's fixed-window rate limiter is built from.
