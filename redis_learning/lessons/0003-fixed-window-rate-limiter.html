Redis Lesson 3: Fixed Window Rate Limiter

Same commands as Lesson 2's debug route — now wired as real allow/deny logic in front of order placement

Where you are

Lesson 2's /api/v1/_debug/redis-demo route already does the entire mechanical core of a fixed-window rate limiter: SET ... NX EX to start a window exactly once, INCR to count within it. It just doesn't decide anything yet — it always returns 200 and lets the request through no matter how high count climbs. This lesson turns that into Express middleware that actually rejects requests with a 429, mounted in front of POST /api/v1/orders — the real order-placement route.

The concept: fixed window, and its one well-known flaw

Fixed window rate limiting has two common variants, both "fixed" in the sense that a window has a hard start and end and the counter simply resets when it ends:

  • Clock-aligned windows — the window is tied to the wall clock (e.g. "the current calendar minute"), typically via a key that encodes the bucket: rate:${id}:${Math.floor(Date.now() / 1000 / windowSeconds)}. Every client sharing that time bucket resets at the same instant.
  • Per-client windows from first request — the window starts whenever that specific client's counter key is first created, and ends windowSeconds later via TTL. This is exactly what SET ... NX EX gives you for free: no bucket math, no key rotation, Redis expires the key and the next request just recreates it.

You're building the second kind — it's the natural fit for the commands Lesson 2 already established, and it's what most simple app-level rate limiters actually ship. The tradeoff to know either way, because it's the reason sliding window (next lesson) exists:

The boundary-burst problem: imagine MAX_REQUESTS = 5, WINDOW_SECONDS = 10. A client sends 5 requests at t=9.9s (right before its window resets), then the window flips at t=10s, and it immediately sends 5 more at t=10.1s. That's 10 requests inside a 0.2 second span, and the limiter allowed every single one — each window individually stayed within its own limit, but nothing bounds the rate across the boundary between two windows. Fixed window guarantees "at most N per window," not "at most N per any N-second span." Keep this in mind; it's exactly what sliding window fixes.

Primary source: Redis Docs — Rate limiting, "Fixed window" section for the algorithm and its boundary-burst tradeoff.

Check your understanding

Q1. In the variant you're building, what starts a given client's window — a shared clock-aligned boundary, or the timestamp of that client's ___ request?

Expected: "first" — SET ... NX only succeeds once per window, on whichever request happens to arrive first after the key expired. Every client's window boundary is its own, not shared with any other client.

Q2. After INCR runs, its return value already includes the current request. If MAX_REQUESTS = 5, should the block-condition compare the count as ___ ___ (not ≥) 5?

Expected: "greater than" — requests 1 through 5 should all be allowed (count reaches 5 on the 5th, still fine), and only the 6th request, where count becomes 6, should be blocked. count > MAX_REQUESTS, not >=.

Q3. What's the name (used above) for the fixed-window flaw where a client can burst up to 2x its limit right across a window's edge?

Expected: "boundary" — the boundary-burst problem. Both windows individually enforce the limit; nothing bounds the combined rate across the seam between them.

The exercise

Two files. Blanks only where a real decision needs to be made — fill them in using what you just read, not by guessing syntax.

1. gateway/src/redis/rateLimiter.ts (new file)

import { Request, Response, NextFunction } from 'express';
import { redisClient } from './client';

const MAX_REQUESTS = ___;    // requests allowed per window — pick something small enough to trigger a 429 by hand
const WINDOW_SECONDS = ___;  // window length in seconds — pick something short enough to test without waiting forever

export async function fixedWindowRateLimiter(req: Request, res: Response, next: NextFunction) {
  const key = `rate-limit:orders:${___}`;  // what identifies "the same client" across requests here?

  const [, count] = await redisClient.multi()
    .set(key, '0', { EX: ___, NX: true })
    .incr(key)
    .exec();

  if (count > ___) {
    const ttl = await redisClient.ttl(key);
    res.set('Retry-After', String(ttl));
    return res.status(___).json({
      error: 'Too Many Requests',
      retryAfterSeconds: ttl,
    });
  }

  ___;  // count is within limit — let the request continue to the proxy
}

Notes on the blanks that aren't just "fill in a number":

  • The client identifier in key — nothing in this repo authenticates callers, so there's no user ID to key on. What does every incoming HTTP request give you, with no auth required, that's at least a reasonable per-caller identifier for a demo like this? (Express puts it on req directly.)
  • The status code — this is a named HTTP status with its own constant meaning "too many requests," not a generic 4xx. Look it up if you don't have it memorized; it's the one this whole lesson has been building toward.

2. gateway/src/index.ts (wire it in front of order placement)

Import fixedWindowRateLimiter, then mount it before the existing orders proxy app.use(...) block — order of app.use calls is execution order in Express, and a rejected request must never reach the proxy. 

app.use('/api/v1/orders', (req, res, next) => {
  if (req.method !== ___) {
    return next();  // only POST (order placement) gets rate-limited — GET lookups pass straight through
  }
  return fixedWindowRateLimiter(req, res, next);
});

// existing app.use(createProxyMiddleware({ ...orders... })) stays right after this, unchanged

Why check the method inside a wrapper here instead of teaching fixedWindowRateLimiter itself about methods: the limiter's job is "count and decide," not "know which routes it applies to" — keeping that logic in the mount point means the same middleware could guard a different method-specific route later without touching rateLimiter.ts at all.

Verify it works

  1. Restart gateway (Redis and the rest of the stack can stay up).
  2. Fire POST http://localhost:3000/api/v1/orders with a JSON body like {"productId": "p1", "quantity": 1, "customerEmail": "a@b.com"}, repeatedly and quickly — past MAX_REQUESTS. A shell loop or hammering the button in a REST client both work.
  3. Confirm the first MAX_REQUESTS calls return 201 (or whatever order-service normally replies), and every call after that returns 429 with a Retry-After header and a body containing retryAfterSeconds.
  4. Confirm GET /api/v1/orders is never rate-limited, no matter how many times you call it — proving the method check actually scopes this to order placement only.
  5. Wait past WINDOW_SECONDS, then hit POST again — it should succeed, proving the window actually reset rather than staying blocked forever.
You now have a real, working fixed-window rate limiter guarding order placement across however many gateway instances might be running — because the counter lives in Redis, not in any one process's memory. You've also felt its one real weakness first-hand (or can reason about it precisely), which is exactly the gap the next lesson closes.
