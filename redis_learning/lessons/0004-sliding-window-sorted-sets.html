Redis Lesson 4: Sliding Window with Sorted Sets

Fixing the boundary-burst problem by tracking individual request timestamps instead of one blunt counter

Where you are

Lesson 3's fixed-window limiter works, but you now know (and can verify yourself) its flaw: a client can send up to 2x MAX_REQUESTS in a short span if it times its bursts around a window boundary, because each window only enforces its own count in isolation. This lesson replaces the single counter with a Redis sorted set (ZSET) — one member per request, scored by the request's timestamp — so the limiter can answer a stronger question: "how many requests has this client made in the last N seconds, as of right now," not "how many requests in whatever window happens to be currently open."

The concept: sliding window log via ZSET

A sorted set stores members with a numeric score, kept in score order, and Redis gives you commands to operate on ranges of that score directly. That maps almost exactly onto "requests in the last N seconds":

  • Score = timestamp. Each accepted-or-rejected request adds one member to the set, scored by Date.now() at the moment it arrived.
  • Member = something unique per request. ZSET members must be unique — adding the same member twice just moves its score, it doesn't create a second entry. Two requests can arrive in the same millisecond, so the timestamp alone isn't safe to use as the member; it needs something appended to disambiguate.
  • ZREMRANGEBYSCORE key 0 windowStart deletes every member older than the window — anything that happened before "now minus N seconds" is no longer relevant and should stop counting.
  • ZCARD key after that trim tells you exactly how many requests fall inside the last N seconds, counted from this exact instant rather than from some fixed clock boundary. This is the number fixed window could never give you.

Because the window boundary moves with every single request instead of jumping in fixed increments, there's no seam for a client to time a burst around — the boundary-burst problem is gone by construction, not by tuning.

The cost: this is more expensive than fixed window on purpose — one ZSET per client instead of one integer, and a remove+add+count on every request instead of a single INCR. Precision traded for cheapness. That tradeoff is exactly why token bucket (next lesson) exists as a third option: it gets sliding-window-like smoothness without storing a full request log.

Primary source: Redis Docs — Rate limiting, "Sliding window log" section for the algorithm and its cost tradeoff vs. fixed window.

Check your understanding

Q1. In this ZSET, the request's timestamp is stored as the member's ___ — the field Redis uses to keep the set ordered and to let you query by range.

Expected: "score" — the timestamp is the score, not the member itself. The member just needs to be a unique string; the score is what ZREMRANGEBYSCORE and range queries actually operate on.

Q2. Why can't the member just be the timestamp on its own, the way the score is? Because two requests arriving in the same millisecond would collide — ZSET members must be ___.

Expected: "unique" — adding a member that already exists just updates its score in place; it does not add a second entry. Two same-millisecond requests with an identical member would silently collapse into one, undercounting.

Q3. In fixed window, retryAfterSeconds came straight from the key's ___ — the whole window resets at one instant, so that value directly answers "when can I try again?". Here, the window boundary moves every request, so that same command no longer answers the question correctly.

Expected: "ttl" — with a moving window, the real "try again in" answer is "when does the oldest request in the set fall out of the window," not the key's TTL (which this limiter has to keep refreshing on every request just to stop the key from lingering forever once a client goes quiet).

The exercise

One new file, plus swapping which limiter is mounted. Blanks only where a real decision needs to be made.

1. gateway/src/redis/slidingWindowRateLimiter.ts (new file)

import { Request, Response, NextFunction } from 'express';
import { redisClient } from './client';

const MAX_REQUESTS = ___;    // same idea as Lesson 3 — requests allowed per window
const WINDOW_SECONDS = ___;  // window length in seconds

export async function slidingWindowRateLimiter(req: Request, res: Response, next: NextFunction) {
  const key = `rate-limit:orders:sliding:${___}`;  // same client identifier as Lesson 3
  const now = Date.now();
  const windowStart = now - WINDOW_SECONDS * ___;  // WINDOW_SECONDS is in seconds, scores are in milliseconds

  const [, , count] = await redisClient.multi()
    .zRemRangeByScore(key, 0, ___)                          // drop anything older than the window
    .zAdd(key, { score: now, value: `${now}-${___}` })      // record this request; needs a unique member
    .zCard(key)                                             // count what's left inside the window
    .expire(key, WINDOW_SECONDS)                            // stop the key from living forever once traffic stops
    .execTyped();

  if (count > ___) {
    const [oldest] = await redisClient.zRangeWithScores(key, 0, 0);
    const retryAfterSeconds = Math.ceil((oldest.score + WINDOW_SECONDS * 1000 - now) / ___);
    res.set('Retry-After', String(retryAfterSeconds));
    return res.status(___).json({
      error: 'Too Many Requests',
      retryAfterSeconds,
    });
  }

  ___;  // within limit — let the request continue to the proxy
}

Notes on the blanks that aren't just "fill in a number":

  • The unique member suffix — anything that won't collide across requests in the same millisecond works (a random value, a counter, whatever you like). The score (now) is what matters for range queries; the member text itself is never read back.
  • zRangeWithScores(key, 0, 0) is given to you as-is — it fetches the single lowest-scored (oldest) member still in the set, which is exactly the request that will be the next one to age out and free up room.

Verify it works

  2. Fire POST http://localhost:3000/api/v1/orders repeatedly and quickly, past MAX_REQUESTS, same as Lesson 3. Confirm you still get 429s with a Retry-After header once you're over the limit.

The actual point of this lesson: reproduce the boundary-burst scenario from Lesson 3 — send MAX_REQUESTS requests, wait until just before you'd expect a fixed window to have reset, then send MAX_REQUESTS more back-to-back. Confirm you now get rejected partway through the second batch, instead of all of them sailing through like they would have under Lesson 3's limiter.
