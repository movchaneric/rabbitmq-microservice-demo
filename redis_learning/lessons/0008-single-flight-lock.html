Redis Lesson 8: Single-Flight Locking (Cache Stampede Prevention)

Closing the gap that cache-aside leaves open: what happens when many requests miss at once

Where you are

Lesson 7 built a working cache-aside read for inventory-service: check cache, hit → return, miss → compute + populate + return. That's correct, but it has a gap. Between "cache says miss" and "cache now has the fresh value," nothing tells any other concurrent request that a refill is already in progress. If ten requests arrive in that window — most realistically, the instant the 10-second TTL expires under load — all ten see a miss, all ten call getStock(), all ten call set(). The last write wins; the other nine were wasted work.

This is harmless right now because getStock() is a cheap in-memory read. The lesson builds the fix anyway, because the fix is the same shape regardless of how expensive the miss path is — and it introduces a genuinely new Redis idiom (using SET as a distributed lock) that's worth having before you hit a real slow backing store.

The concept: cache stampede (a.k.a. dogpile / thundering herd)

A cache stampede is what happens when a single key's expiration causes many concurrent callers to independently decide "not in cache → I'll go compute it," instead of one caller computing it and the rest waiting for that result. Cache-aside as built in Lesson 7 has no mechanism for callers to coordinate — every miss is handled in total isolation from every other miss happening at the same moment.

The fix is single-flight: only one request is allowed "in flight" recomputing a given key at a time. Everyone else either waits for that one request to finish and reads its result from cache, or (if it's taking too long) falls back to computing directly rather than blocking forever.

How do you coordinate across separate Node processes with no shared memory? You can't use an in-process flag (a boolean, a Map of in-flight promises) — that only coordinates requests within one process, not across every instance of inventory-service you might be running. You need the coordination to live somewhere all instances can see it: Redis itself. A lock is just a key that says "someone is already handling this" — and SET with the right options can create that key only if it doesn't already exist, atomically, which is exactly the primitive a lock needs.

New Redis client calls this lesson uses

redisClient.set() you've used since Lesson 7, but only with an expiration option. This lesson adds a second option, condition, used together with expiration for the first time — worth spelling out precisely since the combination is what makes it work as a lock:

  • redisClient.set(key: string, value: string, options?: { condition?: 'NX' | 'XX', expiration?: { type: 'EX'|'PX'|'EXAT'|'PXAT', value: number } }): Promise<string | null> — with condition: 'NX' ("set if Not eXists"), the key is only written if it doesn't already exist. Resolves to "OK" if the write happened (you got the lock) or null if the key was already there (someone else has the lock) — the same hit/miss-shaped signal you already branch on for the cache read itself, just reused for a different purpose. Pairing it with expiration: { type: 'PX', value: ms } gives the lock a millisecond-precision TTL, so if the process holding the lock crashes before releasing it, the lock still expires on its own instead of blocking every future request forever.
  • redisClient.del(key: string): Promise<number> — brand new this lesson. Deletes the key and resolves to the number of keys actually removed (1 if it existed, 0 if it didn't). This is how the lock holder releases the lock as soon as it's done, instead of making every other waiter sit through the full lock TTL even after the real work already finished.

Check your understanding

Q1. redisClient.set(lockKey, "1", { condition: "NX", ... }) is called, but the lock key already exists. What does the call resolve to?

Expected: "null" — the same null-means-"didn't happen" shape as a cache-miss GET. That's the signal you branch on to decide "I got the lock" vs. "someone else has it."

Q2. Why does the lock key need a PX expiration at all, if the code already calls del() right after finishing?

Expected: something like "in case the lock holder crashes" — if the process dies, throws before reaching del(), or otherwise never releases the lock, an unexpiring lock key would block every future request forever. The TTL is the self-healing safety net.

Q3. redisClient.del(key) is called on a key that doesn't exist (already expired or never set). What does it resolve to?

Expected: "0" — the count of keys actually removed, not a boolean and not an error. Calling del() on a non-existent key is always safe.

The exercise

1. inventory-service/src/redis/stockCache.ts (edit)

Same file as Lesson 7. The cache hit/miss branch you already have stays exactly as-is — everything new happens inside the miss branch, which now tries to acquire a lock before recomputing. Blanks are the lock set, its condition/expiration type, and the del that releases it. The retry-loop shape (waiting for whoever did get the lock) and the give-up fallback are given as full code — the control flow is the new concept here, not something to reverse-engineer from a blank. 

import { redisClient } from "./client";
import { getStock } from "../data";
import { Stock } from "../types";

const CACHE_KEY = "cache:inventory:stock";
const CACHE_TTL_SECONDS = 10;

const LOCK_KEY = "lock:inventory:stock";
const LOCK_TTL_MS = 2000;
const RETRY_DELAY_MS = 50;
const MAX_RETRIES = 20;

function sleep(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function fetchAndCache(): Promise<Stock> {
  const stock = getStock();
  await redisClient.set(CACHE_KEY, JSON.stringify(stock), {
    expiration: { type: "EX", value: CACHE_TTL_SECONDS },
  });
  return stock;
}

export async function getCachedStock(): Promise<Stock> {
  const cached = await redisClient.get(CACHE_KEY);

  if (cached) {
    console.log("[cache] hit");
    return JSON.parse(cached) as Stock;
  }

  console.log("[cache] miss");

  // Try to become the single flight that recomputes this key.
  const gotLock = await redisClient.___(LOCK_KEY, "1", {
    condition: "___",
    expiration: { type: "___", value: LOCK_TTL_MS },
  });

  if (gotLock) {
    console.log("[lock] acquired, computing fresh value");
    try {
      return await fetchAndCache();
    } finally {
      await redisClient.___(LOCK_KEY);
    }
  }

  // Someone else has the lock — wait for them to finish and read their result.
  console.log("[lock] held by another request, waiting...");
  for (let i = 0; i < MAX_RETRIES; i++) {
    await sleep(RETRY_DELAY_MS);
    const retryCached = await redisClient.get(CACHE_KEY);
    if (retryCached) {
      console.log("[cache] hit after wait");
      return JSON.parse(retryCached) as Stock;
    }
  }

  // Gave up waiting (lock holder is unexpectedly slow or stuck) — compute directly
  // as a safety valve rather than hang the request forever. Deliberately does not
  // write to cache: the lock holder owns that, and writing here would defeat the
  // single-flight guarantee if it finishes right after.
  console.log("[lock] gave up waiting, computing directly");
  return getStock();
}
A subtlety this exercise leaves unsolved: the del(LOCK_KEY) in the finally block deletes the lock unconditionally. If this request's lock happened to expire (hit the full LOCK_TTL_MS) right before fetchAndCache() finished, another request could have already acquired a new lock — and this del() would delete that other request's lock instead of its own. The fully correct fix stores a unique value in the lock (e.g. a random ID per request) and only deletes if the current value still matches that ID — node-redis actually ships a command for exactly this compare-and-delete, delEx(key, { condition: "IFEQ", matchValue }). Not required for this exercise (2 seconds is generous for a read this cheap, so the race is very unlikely to matter here), but worth knowing the gap exists before relying on this pattern for something slower.

Verify it works

  1. Restart inventory-service so the new code is loaded.
  2. Let the cache expire (wait 10+ seconds without hitting the route, or redis-cli DEL cache:inventory:stock to force it).
  3. Fire several concurrent requests at once, e.g. for i in 1 2 3 4 5; do curl -s http://localhost:3002/inventory & done; wait. Watch the terminal log: you should see exactly one [lock] acquired, computing fresh value, and the others should show [lock] held by another request, waiting... followed by [cache] hit after wait.
  4. redis-cli GET lock:inventory:stock right after should come back empty — confirms del() released it instead of waiting out the full TTL.
  5. All five responses should still contain identical, correct stock data — the lock changes who computes the value, never what value gets returned.
inventory-service's cache-aside read is now stampede-safe: a cold cache under concurrent load triggers exactly one recompute, not N. The mechanism — SET ... NX as an atomic "claim this work" primitive, paired with a TTL as a crash-safety net — is the same shape used for distributed locks generally, not just caching.
