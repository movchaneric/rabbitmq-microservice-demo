Redis Lesson 9: Write-Path Cache Invalidation

When TTL-only isn't safe anymore — clearing the cache the instant data changes, instead of waiting out the window

Where you are

order-service now has its own redis/getCachedOrders.ts, built by mirroring Lessons 7 and 8 directly onto a second service: cache-aside for GET /orders, plus the same SET ... NX single-flight lock so concurrent misses don't all recompute at once. Same shape, new service — nothing new to teach in the mechanism itself.

But porting the shape over also silently ported over an assumption that doesn't hold here. Lesson 7 justified TTL-only invalidation for inventory-service explicitly: "nothing in this codebase currently mutates stock on order placement." That justification was specific to inventory — it does not transfer to orders. addOrder() in order-service/src/data.ts mutates the underlying array on every successful POST /orders. Left as TTL-only, a freshly placed order would be invisible from GET /orders for up to CACHE_TTL_SECONDS (10s) after creation — the cache would be confidently wrong, not just eventually catching up.

The concept: two invalidation strategies, and the trade they represent

There are two fundamentally different ways a cache entry can become correct again after the underlying data changes:

  • Lazy / TTL-only (Lesson 7's approach): the entry expires on its own after a fixed window; nothing on the write path needs to know the cache exists at all. Staleness is bounded (never worse than the TTL), coupling is zero. Correct choice specifically because inventory's write path never touched the cached data.
  • Active invalidation on write (this lesson): the write path explicitly deletes (or updates) the cache entry the moment the underlying data changes, so the next read is guaranteed fresh rather than "fresh within N seconds." This requires the write path to know the cache exists — a piece of coupling Lesson 7's approach was specifically designed to avoid.
This is the classic "cache invalidation is hard" problem, in miniature. The reason cache invalidation has a reputation as one of the two hard problems in computer science isn't the mechanism (it's one line: delete the key) — it's coverage. Every single write path that touches the cached data has to remember to invalidate it, and missing even one silently reintroduces stale reads with no error, no crash, nothing to point at the bug. order-service currently has exactly one write path (addOrder(), called from one place in index.ts), so the "did I get all of them?" question has an easy answer right now. It won't stay easy forever — every future write path added to this service needs the same discipline applied to it, or the cache silently drifts from the truth again.

Redis client calls this lesson uses

None new. redisClient.del(key) is the exact same command from Lesson 8 — there it deleted a lock key to release coordination; here it deletes a cache key to force staleness. del() doesn't know or care why a key is being removed — worth noticing that the same primitive serves two conceptually different jobs depending on which key you point it at.

Check your understanding

Q1. Right after a successful POST /orders with invalidation wired up, what should redis-cli GET order:list show?

Expected: "nil" / nothing — the key was just deleted. The next GET /orders will see a cache miss and repopulate it with the up-to-date list, including the order you just placed.

Q2. Why shouldn't invalidateOrdersCache() be called from inside addOrder() in data.ts, rather than from the route handler in index.ts?

Expected: something like "data.ts is the source of truth / shouldn't know about caching" — same reasoning as getStock() never touching Redis directly. Keeping the data layer cache-unaware means the caching concern stays isolated to the redis/ modules and the route layer that orchestrates them, instead of leaking into the one place that's supposed to be the plain, boring source of truth.

Q3. If invalidateOrdersCache() is called without await (fire-and-forget) right before the response is sent, what's the risk, compared to awaiting it?

Expected: something like "a brief staleness window / race" — a concurrent GET /orders arriving in the tiny gap between "response sent" and "delete actually applied" could still see the old cached list. Awaiting it closes that gap at the cost of a small amount of added latency on the write.

The exercise

1. order-service/src/redis/getCachedOrders.ts (edit)

Add one new exported function. Full code — del() is already a practiced command from Lesson 8, so there's no new mechanism to retrieve here, just a new place to apply it. 

export async function invalidateOrdersCache(): Promise<void> {
  await redisClient.del(CACHE_KEY);
}

2. order-service/src/index.ts (edit)

Import invalidateOrdersCache, and call it in the POST /orders success branch, right after addOrder(order) — that's the exact moment the underlying data actually changed. The publish callback needs to become async to await it. 

import { invalidateOrdersCache } from "./redis/getCachedOrders";

// ...inside the channel.publish(...) callback, two changes:

//  2. inside the success branch, after addOrder(order):
async (err) => {

  } else {

Verify it works

  1. Restart order-service.
  2. GET http://localhost:3001/orders once — populates the cache. Note how many orders come back.
  3. POST http://localhost:3001/orders with a new order body.
  4. Immediately (well within 10 seconds): redis-cli GET order:list — should be empty/nil, proving invalidation actually fired instead of waiting out the TTL.
  5. GET /orders again — the new order should already be in the list, even though the old TTL window hasn't elapsed. Compare this to what would've happened with TTL-only: the new order would be invisible for up to 10 more seconds.
order-service's cache-aside read is now correctly invalidated on write — no blind spot between placing an order and seeing it reflected in GET /orders. More importantly, you've now built both ends of the invalidation spectrum with real justification for each: TTL-only where the write path never touches the cached data (inventory), active invalidation where it does (orders).
